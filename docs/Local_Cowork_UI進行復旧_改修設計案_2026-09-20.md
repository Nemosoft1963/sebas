# UI上で計画修正・検証・実行へ進める改修設計案

日付: 2026-09-20。検討のみ。コード変更・外部送信・本番実行なし。

## 結論

実現可能。既存APIと画面を再利用できる。ただし画面表示の改善だけで解決する部分と、バックエンドの構造的な計画修正・再開接続が必要な部分を分ける。未実装能力をボタンで実行可能に見せない。

## 現行実装で確認した問題

app/static/goal_review.jsには指摘取込、修正案作成、反映、外部検証の操作が既に存在する。修正案にblockersがあると反映ボタンを無効化するが、次に誰が何をすれば解消するかの統一した導線がない。ステータスと指摘・修正・成果物が複数領域に分散し、外部結果はJSON中心。

定期処理はプロジェクト選択の変化を監視するだけで、同じ案件の検証完了・予算待ち解消を自動取得しない。action終了時には一律ボタン有効化後に一部だけ条件を戻すため、操作可否を一元管理できていない。

app/static/artifact_shelf.jsでは自動抽出と確認UIが別領域。確認事項の会社・月・原本の事情と、計画の外部検証待ちが一つの進行状態として提示されない。

利用可能API: goal-review、feedback/import・propose・apply、goal-review/plan、queue/cancel、vehicle-profit、prepare、decision。既存の計画承認・実行APIも、その権限・版照合を維持して接続する。新設名は以下の提案であり、現在存在するAPIと混同しない。

## 提案画面

案件の先頭に「現在の状態と次の操作」を常時表示する。

表示例:
- 目標: 2026年1〜7月の車両別損益Excel
- 現在: 計画の修正・再検証が必要
- 主な停止理由: 現行計画の外部検証未実施／追加開発が必要な指摘あり
- 次の操作: 修正できる指摘から計画修正案を作成
- 補足: 残る開発課題は修正案だけでは解消しません

工程表示: 原本確認 → 計画修正 → 外部検証 → 実行承認 → Excel生成 → 原本照合 → 人間確認・再利用。
各工程には未着手・処理中・確認待ち・失敗・完了を表示。暫定Excel生成を目標達成扱いにしない。

## 状態ごとの操作

|状態|表示する次の操作|必要な接続|
|旧計画・実行工程不足|現行機能に合わせた計画修正案を作る|実行契約と依存関係を更新する計画修正処理|
|外部指摘あり|修正可能項目をまとめて修正案へ|既存proposeを再利用。対応不能は開発課題として分離|
|修正案あり|変更前後・目標との対応を確認して反映|既存apply。反映後は新しい版の検証準備へ|
|未検証・旧版検証|送信内容を確認して外部検証|公開用説明を再生成し、明示された送信承認範囲を確認|
|予算待ち|次回時刻・待ち内容・取消|既存キュー。ユーザーに繰り返し押させない|
|検証合格・未承認|この計画を承認して実行|承認と実行の版を一致させる。既に有効な承認は再要求しない|
|原本の業務事実不足|月・金額・原本を見て必要箇所のみ回答|ユーザー確認とシステム修正を分離|
|読取・検証失敗|原因・修復状況・再試行の条件を表示|読取不能0円化等を先に修正。TRIZは接続済み範囲のみ使用|
|暫定Excelあり|暫定結果を開く／残課題を見る|未配賦・仮定ゼロ・照合未了を明示|
|全検証合格|成果物を確認して再利用登録|人間確認を維持。手順の実行再利用は別途実装が必要|

## 指摘対応表

各指摘に「対象目標・工程／修正内容／状態／根拠／次の操作」を表示する。状態は自動修正可能、修正案確認待ち、追加開発必要、業務事実確認待ち、修正済み再検証待ち、検証済みに分ける。

開発課題をユーザーへの入力質問に変換しない。文章への追記だけで解決済みにせず、実行契約と検査結果を根拠にする。未解決課題がある場合、安全な部分修正を保存できる設計を検討するが、実行条件の解除とは分離する。

## 必要なバックエンド変更

1. 統合進行状態API（提案: GET /api/projects/{id}/workflow-readiness）。既存の実行ゲートと同じ判定を共有し、plan_version、signature、blockers、allowed_actions、next_action、active_job、成果物の暫定/確定区分を返す。UI側で合格判定を再実装しない。
2. 修正・検証・実行の長時間処理をジョブとして追跡。job_id、進捗、エラー、更新時刻を返す。再読込で復元し、二重クリック・再送で二重実行しない。
3. 目標・原本・計画版が変わったら古い結果の適用を拒否し、再確認が必要な理由を表示。部分失敗は最後の有効状態から再開する。
4. 画面表示中かつ処理中は数秒間隔の状態取得またはイベント通知。非表示時は抑制し、通信失敗を「処理失敗」と混同しない。
5. 修正完了から送信準備まで自動でつなぐ。外部送信は送信内容と承認範囲を維持し、変更後の内容へ古い承認を無条件流用しない。
6. TRIZの候補保存と実行回復を別状態にする。業務検査に合格し採用済みになるまでは「回復成功」と表示しない。

## 実装順序

第一段階: 統合停止理由・次の操作・ボタン可否・状態更新。既存APIを再利用でき、比較的小規模。停止原因が見えるが業務完了を保証する段階ではない。
第二段階: 計画更新、指摘反映、再検証、承認・実行の連結とジョブ管理。実際に先へ進むための中規模改修。
第三段階: 月別配賦、TRIZ回復、実行手順再利用。個別バックエンド実装と受入試験が必要。

第一段階と並行して、再監査で判明した読取不能の0円化、原本合計照合欠落、粗い重複判定を修正する。これらが残った状態を「確定生成が可能」としてリリースしない。日数見積もりは実行・承認系の追加調査後に確定する。

## 受入条件

- 現在のv24を開くと、未検証・未解決指摘・未実行を区別して次の操作が見える。
- 修正→反映→再検証→承認→実行を、JSON編集や回答の手動転記なしで追跡できる。
- 開発未対応時に実行可能と表示せず、根拠のある開発課題を示す。
- 予算待ちからの進展が手動更新なしで表示される。二重送信・二重実行を防ぐ。
- 原本・計画変更時は古い画面の操作を拒否して最新状態へ案内する。
- 読取不能や照合不一致があれば、暫定成果物を残しつつ確定完了・成功RAG登録を阻止する。
- 実原本を通常の計画実行経路で処理し、Excelと独立した原本照合記録まで確認する。

本設計は検討結果であり、UIへの反映はまだ実施していない。
