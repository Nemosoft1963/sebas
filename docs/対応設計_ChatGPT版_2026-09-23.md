## 2. P0-1 金額の欠損・読取失敗・実額ゼロの分離

### 現状再確認

提案は現コードと一致し、未修正である。

- `app/vehicle_auto.py` `text()`（約16行）: `str(value or '')` のため、数値 `0` と `False` を空文字へ変換する。
- 同 `money()`（約24行）: 上記の影響で `money(0)` は `None`、`money('0')` は `0` となる。
- 同 `Extractor.add()`（約122〜145行）: `amount is None` の場合、計算済み値のない数式セル以外は何も記録せずreturnする。非空の「要確認」等も黙って脱落する。
- 同 `master()`、`payroll()`、`generic()`（約204〜258行）: セル値を `money()` に通し、失敗理由や元値種別を渡さない。
- 同 `fuel()`（約260〜330行）: CSV金額失敗はissueを作るが、Excel系との表現が統一されておらず、空欄・不正値・数式キャッシュなしの分類も共通化されていない。
- 同 `finish()`（約331〜359行）: 存在しない車両・月・費目を `assumed_zero` で補完する。先に非空不正値が脱落しているため、読取失敗が「対象明細なし」に見えて仮定ゼロへ置換され得る。
- `app/vehicle_profit.py` `calculate()`（約18〜99行）: `actual`、`estimated`、`missing`、`assumed_zero` は扱えるが、「原本に値はあるが読取失敗」を表す入力モデルがない。
- 既存テスト `tests/test_vehicle_auto.py` には数式キャッシュ欠落の試験はあるが、数値0、文字列0、空欄、非数値を横並びで区別する試験はない。

### 設計方針

#### 2.1 金額読取結果を型付きで返す

`money(value)` の曖昧な `int | None` を直接業務判断へ使わず、次の構造を返す純粋関数を新設する。

```python
@dataclass(frozen=True)
class MoneyParseResult:
    status: Literal['value', 'blank', 'invalid', 'formula_missing']
    amount: int | None
    raw_text: str
    raw_type: str
    reason: str = ''


def parse_money(value, *, formula_missing: bool = False) -> MoneyParseResult: ...
```

互換性のため `money()` を直ちに全面削除せず、内部で `parse_money()` を呼んで `status == 'value'` の金額だけを返す薄い関数にできる。ただし抽出器は必ず `parse_money()` を使用する。

分類規則:

- Pythonの `0`、`Decimal('0')`、文字列 `'0'`、`'0円'`: `status='value', amount=0`
- `None`、空文字、空白だけ: `status='blank'`
- 非空の非数値（例: `要確認`）: `status='invalid'`
- 数式セルでキャッシュ値なし: `status='formula_missing'`
- 範囲外、NaN、真偽値: `invalid`。真偽値を0/1として扱わない。

`text()` 自体も `None` だけを空文字にし、数値0を保持する実装へ変更する。ただし金額以外の呼出箇所への影響をテストする。

#### 2.2 抽出明細と読取問題を分離保存する

`Extractor.add()` を次へ変更する。

```python
def add(
    self, source, locator, mon, category,
    parsed: MoneyParseResult,
    targets, comp='', basis='inclusive', **extra
) -> None:
```

- `value`: `quality='actual'` のrecordを作る。0円も原本参照付きactualとして保持。
- `blank`: recordを作らない。ただし後段の不足判定候補として `(vehicle, month, category)` のblank観測を保持する。
- `invalid` / `formula_missing`: `read_failure` を作り、`source_ref`、`source_locator`、`month`、`category`、`raw_text`、`reason`、可能なら車両候補を保存する。確定阻害issueとする。

`auto_extraction` を次のように拡張する。

```json
{
  "version": "vehicle-auto-v2",
  "issues": [],
  "read_failures": [
    {
      "id": "...",
      "source_ref": "context:...",
      "source_locator": "Sheet!C12",
      "month": "2026-01",
      "category": "fuel",
      "raw_text": "要確認",
      "reason_code": "non_numeric",
      "status": "unresolved"
    }
  ]
}
```

入力schemaは `vehicle-profit-input-v2` へ上げる案を推奨する。移行期間はv1を読めるようにするが、自動抽出出力はv2のみとする。

#### 2.3 仮定ゼロの適用条件を厳格化する

`finish()` の0円補完条件を「actual明細がない」だけから次へ変更する。

- 同じ原本範囲・車両・月・費目に未解決 `read_failure` がない。
- 同じ費目に未配賦recordがない。
- 原本照合が、その範囲に未取得金額がないことを示す、または業務上の不足0円方針が適用可能。
- 読取アダプター未対応の原本が、その費目・月を含む可能性がない。

`assumed_zero` に `zero_reason_code='authorized_missing'` と適用した要求ハッシュを保存する。読取失敗・未配賦・照合不能は0円で解消しない。

#### 2.4 検証器の変更

- `vehicle_auto.evidence_issues()` は未解決 `read_failures` を確定阻害する。
- `vehicle_profit.calculate()` は必要なら `quality='read_failure'` をrecordに追加せず、抽出メタデータ側で阻害する。計算recordへ混ぜる場合は `amount=None` を必須にし、missingと別区分にする。
- Excel「不足と未配賦」シートへ、欠損、読取失敗、数式未計算、未配賦、仮定ゼロを別表示する。

### 変更対象ファイル

- `app/vehicle_auto.py`
  - `text`, `money`, 新規 `parse_money`
  - `Extractor.add`, `master`, `payroll`, `generic`, `fuel`, `finish`, `evidence_issues`
- `app/vehicle_profit.py`
  - `calculate`, `build_workbook` の例外区分表示
- `app/vehicle_workflow.py`
  - `normalize_input`, `validate_evidence` のschema・読取失敗検査

### 受入条件の検証方法

1. 同じExcel列に数値0、文字列0、空欄、`要確認`、キャッシュ値なし数式を置く。
   - 数値0と文字列0はactual 0円、原本セル付き。
   - 空欄だけが不足候補。
   - `要確認` はread_failure。
   - 数式キャッシュなしはformula_missing。
2. `zero=True` でも `要確認` と数式欠落の対象費目に `assumed_zero` が作られないことを確認する。
3. actual 0円がExcel「入力明細」「原本対応」に残り、「仮定ゼロ」と表示されないことを確認する。
4. 未解決read_failureがある場合、暫定Excelは保存できても `status='completed'` と最終検証は通らないことを確認する。
5. 空欄で不足0円指示がある場合だけ `assumed_zero` となり、要求ハッシュと理由が保存されることを確認する。
6. 既存の正の金額、負額、桁区切り、円記号、範囲外値の回帰試験を行う。

## 3. P0-2 原本と出力の独立した金額照合

### 現状再確認

提案は現コードと一致し、未修正である。

- `app/vehicle_auto.py` `finish()`（約359行）: 自動抽出結果は常に `source_controls=[]`。
- `app/vehicle_workflow.py` `validate_evidence()`（約148〜199行）: `auto_extraction` がある場合は `vehicle_auto.evidence_issues()` へ即returnし、通常入力用のsource_controls検査を通らない。
- 同 `execute()`（約285行）: `checks['source_controls'] = not validate_evidence(...)` のため、自動経路のissuesが空ならsource_controlsが空でもtrueになる。
- 同 `goal_failures()`（約205〜246行）: `checks.source_controls` を必須にしているが、上記の誤ったtrueを信用する。
- `app/vehicle_profit.py` `calculate()`（約92〜99行）のreconciliationは「正規化済み入力 = 配賦済み + 未配賦」の算術照合であり、原本合計との独立照合ではない。
- 同 `build_workbook()`（約100〜180行）のExcel再計算も同じ正規化入力に対する計算一致であり、抽出漏れを検出できない。

### 設計方針

#### 3.1 原本統制値を独立データとして保存する

`source_controls` を空配列前提から、取得可否を含む構造へ変更する。

```json
{
  "source_ref": "context:...",
  "company": "関東",
  "month": "2026-01",
  "category": "fuel",
  "tax_basis": "inclusive",
  "control_kind": "invoice_total",
  "amount": 123456,
  "source_locator": "請求書1頁 合計",
  "extraction_method": "invoice_header_adapter:v1",
  "status": "available"
}
```

取得できない場合も行を残す。

```json
{
  "source_ref": "context:...",
  "company": "関東",
  "month": "2026-01",
  "category": "fuel",
  "status": "unavailable",
  "reason_code": "no_independent_total",
  "reason": "明細のみで請求総額欄がない"
}
```

原本別・会社別・月別・費目別・税区分をキーとし、重複controlを禁止する。請求単位が存在する費目はP0-3のinvoice_idもキーに含め、最終的に上位集約する。

#### 3.2 照合結果を明示保存する

新規純粋関数を `vehicle_workflow.py` または専用 `vehicle_reconciliation.py` に置く。

```python
def reconcile_sources(
    records: list[dict],
    controls: list[dict],
    dispositions: list[dict],
    excluded_records: list[dict],
) -> list[dict]:
```

各キーで次を計算する。

- `source_total`: 原本統制額
- `included_total`: 取り込みrecord額
- `excluded_total`: 金額と根拠を持つ対象外額
- `unallocated_total`: 取り込み済みだが車両未配賦の額（included_totalの内数として別表示）
- `unread_total`: read_failure等で金額不明なら数値化せず `unknown_components > 0`
- `difference = source_total - included_total - excluded_total`
- `status`: `matched | mismatched | unavailable | incomplete`

未配賦は抽出漏れではないため原本対取り込み照合ではincludedに含めるが、車両損益確定ゲートでは別途阻害する。除外は金額、原本位置、理由、承認主体を持つ場合のみ差引可能とする。

#### 3.3 確定ゲートを一本化する

`validate_evidence()` の自動・手入力分岐を廃止し、共通検証へ統合する。

- 全対象sourceにdispositionがある。
- 必要なcontrolが `available`。
- reconciliationが全件`matched`。
- controlのない対象は`unavailable`として明示され、確定不可。
- read_failure、未根拠除外、重複control、対応明細なしcontrolは確定不可。

チェックを真偽値だけでなく次の構造で保存する。

```json
"checks": {
  "source_reconciliation": {
    "passed": false,
    "matched": 10,
    "mismatched": 1,
    "unavailable": 2,
    "artifact": ".../source_reconciliation.json"
  }
}
```

互換用 `source_controls: bool` は段階的に廃止する。`goal_failures()` は詳細チェックの `passed is True` のみを合格とする。

#### 3.4 Excelへ独立照合を表示する

`build_workbook()` に照合結果を渡し、「原本照合」シートへ原本総額、取込、根拠付き除外、差額、未配賦、状態、原本位置を出す。現在の「照合」シート（入力対配賦）とは分離し、名称も「配賦照合」とする。

### 変更対象ファイル

- `app/vehicle_auto.py`
  - 各アダプターでcontrol抽出、`finish()` のsource_controls生成
- `app/vehicle_workflow.py`
  - `validate_evidence`, `execute`, `goal_failures`
  - 新規 `reconcile_sources` または専用モジュール呼出し
- `app/vehicle_profit.py`
  - `build_workbook` の原本照合シート
- `tests/test_vehicle_workflow.py`
- `tests/test_vehicle_auto.py`
- `tests/test_vehicle_integration.py`

### 受入条件の検証方法

1. 原本統制額1000円、明細600円+400円でmatchedとなる。
2. 400円明細を欠落させ、差額400円・mismatchedとなり確定完了を阻止する。
3. 同一明細を重複させ、差額-400円を検出する。
4. 100円を根拠付き除外すると、取込900円+除外100円でmatchedとなる。理由または原本位置を欠く除外は不合格。
5. controlを取得できない原本は `unavailable` と表示し、空配列を合格扱いしない。
6. 未配賦額は原本対取込では欠落扱いにせず、車両別確定ゲートでは阻害することを確認する。
7. Excel再計算とPython計算が一致しても、source reconciliation不一致なら最終検証が失敗することを確認する。
8. 会社・月・費目が同じでもsource_refまたはinvoice_idが異なる統制値を混同しないことを確認する。

## 4. P0-3 請求単位の重複判定と部分抽出検知

### 現状再確認

提案は現コードと一致し、未修正である。

- `app/vehicle_auto.py` `extract()`（約393〜425行）:
  - `vendor + company + month` の3要素をkeyとする。
  - 同keyのCSVが1件でもparseされるとPDFを除外する。
  - `請求書(鑑)` を無条件除外する。
  - 請求番号、請求総額、明細集合を比較しない。
- 同 `fuel()`（約260〜330行）:
  - 1件以上recordが増えると成功を返す。
  - 期待明細件数、ページ範囲、請求総額との差額を確認しない。
  - 一部だけ正規表現に合致したPDFも全体成功に見える。
- 既存 `test_csv_pdf_duplicate_is_not_double_counted()` は、同月PDFを除外する現在の粗い挙動を正解として固定しており、修正後は置換が必要。

### 設計方針

#### 4.1 請求文書メタデータを先に抽出する

燃料原本ごとに、明細抽出とは別に次を返す。

```python
@dataclass
class InvoiceDocument:
    source_ref: str
    vendor: str
    company: str
    billing_month: str
    invoice_number: str | None
    invoice_date: str | None
    printed_total: int | None
    detail_count_printed: int | None
    document_role: Literal['detail', 'cover', 'combined', 'unknown']
    detail_fingerprints: list[str]
    extraction_complete: bool
    extraction_issues: list[dict]
```

明細fingerprintは、可能な範囲で `日付、車番、商品、数量、税、金額` の正規化値から作る。sourceファイル名や行番号だけを同一性根拠にしない。

#### 4.2 重複判定を証拠付きにする

新規関数:

```python
def classify_invoice_relation(a: InvoiceDocument, b: InvoiceDocument) -> Literal[
    'exact_duplicate', 'same_invoice_complement', 'different_invoice',
    'partial_overlap', 'unknown'
]:
```

優先規則:

1. vendor/company/invoice_numberが一致し、printed_totalと明細集合も一致 → exact_duplicate。
2. 請求番号一致、CSVとPDFが相補的で総額一致 → 同一請求の表現違い。明細精度が高い方を計上し、他方はcontrol証拠。
3. 同月でも請求番号が異なる → different_invoiceとして両方保持。
4. 請求番号なしでも明細集合・合計が完全一致 → exact_duplicate候補。ただし根拠を保存。
5. 一部だけ一致、合計差あり → partial_overlap。自動除外せず確定阻害。
6. 比較不能 → unknown。二重加算を避けた暫定選択は可能だが、確定不可。

`source_dispositions` に `duplicate_of`、`relation`、比較した請求番号・総額・fingerprint件数を保存する。

#### 4.3 請求書鑑をcontrolとして使用する

`document_role='cover'` は明細計上しないが、無条件の「重複除外」ではなく、請求総額controlとしてP0-2へ渡す。明細CSV/PDF合計と鑑総額を照合し、差額を保存する。

#### 4.4 部分抽出を検出する

アダプター結果をboolから次へ変更する。

```python
@dataclass
class AdapterResult:
    matched: bool
    records_added: int
    parsed_total: int
    printed_total: int | None
    expected_detail_count: int | None
    parsed_detail_count: int
    complete: bool
    issues: list[dict]
```

`complete` は少なくとも次のいずれかを満たす場合のみtrue。

- 明細数と総額が原本表示と一致。
- 総額のみ存在し、抽出明細合計と一致し、未解析領域がない。
- vendor固有の終端・ページ・小計検査をすべて通過。

1件でも読めた、という条件だけではcompleteにしない。

  - 新規 `InvoiceDocument`, `AdapterResult`, invoice比較関数

### 受入条件の検証方法

1. 同じvendor/company/monthで請求番号が異なるCSVを2件入力し、両方が保持される。
2. 同一請求番号・同一明細・同一総額のCSVとPDFは1回だけ計上し、PDF/鑑をcontrol証拠として残す。
3. CSVが明細2件、PDF/鑑が3件・総額差ありの場合、partial_overlapと差額を検出し確定を阻止する。
4. 請求番号なしでも完全一致する明細集合を重複と判定できるが、その根拠が保存される。

1. feedback import

3. human confirmation
4. apply
5. public packet regeneration
6. explicit send approval
7. external re-review / budget queue
8. plan human approval
9. execution start

外部送信はstep 6なしに自動遷移しない。packet hash、provider一覧、公開用本文を承認記録へ含める。plan/source/requirements hashが変わればstep 5へ戻す。

#### 6.4 再開位置を保持する

workflow instanceへ `last_completed_stage` と `blocking_error` を保存する。ローカルproposal失敗は再生成、外部送信後の不明状態はneeds_attention、予算不足はwaiting_budget、実行失敗はmission task状態へ接続する。

### 現状再確認

### 設計方針

#### 7.1 配賦ルールを一次データ化する

```json
{
  "id": "allocation-rule-...",
  "subject_type": "employee|invoice_detail|cost_pool",
  "subject_key": {"company": "関東", "employee": "山田太郎"},
  "effective_from": "2026-01-01",
  "effective_to": "2026-03-31",
  "allocations": [
    {"vehicle_id": "...", "ratio": "0.6"},
    {"vehicle_id": "...", "ratio": "0.4"}
  ],

  "reason": "...",
  "source_hash": "...",
  "requirements_hash": "...",
  "created_by": "human|source_rule",
  "status": "active"
}
```

期間は日付または月単位とし、月中乗替を日付で扱う必要があるかは業務仕様確認事項とする。ratio合計1、会社整合、期間重複をvalidatorで検査する。

#### 7.2 issue単位の回答APIへ変更する

`decide()` を単一vehicle_idから複数配賦へ拡張する。

```python
def decide(
    manager, pid, version, input_hash, issue_id,

```

`decision` は対象record IDsまたは期間を明示し、group全件を暗黙適用しない。UIでは月別行を展開し、複数車両と比率を入力できる。

#### 7.3 判断継承を適合性評価付きで行う

再抽出時に旧判断を次の条件で再評価する。

- subject keyが同じ。
- 対象月が有効期間内。
- vehicle IDと会社が現行対象集合に存在。
- 根拠sourceのhashが同じ、または原本変更後も再確認済み。
- 対象recordの安定fingerprintが一致。
- 要求hash変更が配賦ルールへ影響しない。

結果を `reused | needs_revalidation | invalid` で保存する。無条件再適用しない。

#### 7.4 社会保険根拠を分離する

insurance recordへ次を必須化する。

```json
"insurance_basis": {
  "kind": "explicit_employer_amount|calculated_from_confirmed_rule",
  "base_amount": 0,
  "rate": null,
  "components": [],
  "source_refs": [],
  "rule_version": null
}
```

当面は `explicit_employer_amount` のみ確定可能とし、本人控除列からの推測を禁止する。料率計算を実装する場合は、対象報酬、標準報酬月額、保険区分、年齢、地域、適用年月、会社負担区分、端数規則を業務仕様として確定してから別adapterで行う。

配賦済みactualが追加された後、同じvehicle/month/categoryの `assumed_zero` を削除する正規化関数を作る。削除履歴はdecision logへ残す。未配賦actualがあるだけでは全車両のzeroを自動削除せず、配賦確定後に行う。

## 14. テスト戦略

### 14.1 単体テスト

- 金額parse状態。

- allocation rule適合性。

- Excel/CSV/PDF合成原本→抽出→照合→暫定/確定判定。
- feedback→apply→signature更新→queue→review→approve→start。
- 再抽出→判断継承/失効。
- failure→TRIZ→試験→採用→限定再実行。
- recipe→別月原本→fresh extraction→照合。

- 状態カード、停止理由、次操作。
- button可否と理由。
- poll、非表示停止、通信失敗。
- 二重クリック・再読込復元。
- 月別複数配賦。

### 14.4 実原本受入

合成データで欠陥を再現・回帰した後に実施する。登録原本を通常計画経路で処理し、次を確認する。

- 対象車両×2026年1〜7月のcoverage。
- 原本別・会社別・月別・費目別・請求別control。
- 差額0または明示された未達。
- 未配賦、read failure、partial invoice、unknown controlの件数。
- Excel再計算と独立Python計算。
- 暫定/確定の正しい区別。

外部検証送信、本番計画実行、配備、サービス起動は別の明示承認を得て行う。
