# 依頼: 機能拡張・改善要望の整理と実行計画の作成(計画のみ、実装はしない)

## 背景
`docs/analysis/` に、3つのAI(Claude・Gemini・Grok)が同一指示で独立に行ったLOCALSAPORTERの
アーキテクチャ調査結果(`claude-20260921-115043.md` / `gemini-20260921-130955.md` / `grok-20260921-131513.md`)と、
その突き合わせ(`comparison-claude-vs-gemini.md`)がある。これが機能拡張・改善要望の記録である。

3者が一致して指摘した主な点(要確認・優先度高):
1. 認証・認可がない(localhostバインドのみが防御境界)
2. `app/web.py` に責務が集中(2917行)
3. 実行モニターの状態(`executions`)がメモリ上のみで、再起動で消える
4. TRIZ収集データの受け口(`POST .../learning/general`)は既存実装として確認済み

Grokのみが指摘した重要な点:
5. `FRONT_AI_PROVIDER` のコード既定が `chatgpt`(compose/.envは`ollama`)。設定漏れで外部AIに送信され得る
6. Dockerイメージタグが未固定(open-webui: main、computer/qdrant: latest)
7. 経験RAGの依存はDocker既定で入らない(`INSTALL_EXPERIENCE_RAG=0`)
8. 承認後メールがSMTP設定次第で実際に外部送信される(`_send_approved_email`)

Claude/Grok一致:
9. `validate_problem` が `None` を文字列 `"None"` にするバグ(`app/triz_common.py`)
10. テスト件数の記録の食い違い(MANIFEST.json=13, SYSTEM_DESCRIPTION_FOR_AI.md=50, BUILD_REPORT.md=403/414)
11. `lifespan` が複数回ラップされる
12. `app/main.py` + `config/settings.yaml` とWeb経路の二重実装
13. `.env.example` の公開事業者情報の配布時の注意

## やること(今回は計画のみ。コード変更は一切しない)
1. `docs/analysis/` の4ファイルすべてを読む。
2. 上記の指摘事項ごとに、次を整理する:
   - 実際に該当コードを読んで、指摘が今も正しいか再確認する(修正済み・誤りがあれば明記)
   - 深刻度(セキュリティ/データ消失リスク/バグ/保守性)
   - 対応の概略案(どのファイルをどう直すか)
   - 対応の順序(依存関係・壊れやすさを踏まえた「触る順序」。各報告書の該当セクションも参考にする)
3. 対応不要と判断したものがあれば、理由とともに明記する。
4. 実行計画として、`docs/改善実行計画_2026-09-23.md` に日本語でまとめて保存する
   (フェーズ分け: 例えば「フェーズ1: セキュリティ・データ消失防止」「フェーズ2: 既定値・設定の安全化」
   「フェーズ3: 保守性・リファクタリング」など)。
