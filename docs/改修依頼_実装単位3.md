# 改修依頼: 実装単位3(P1-1 UIの停止理由と次の操作を統合、第一段階)

## 背景
`docs/対応設計_最終版_2026-09-23.md` 第4章(P1-1)・第11章「実装単位3」に従う。
P0-1〜P0-3(単位0・1・2A・2B・2C)は実装済み・全体481件合格・Dockerビルド/healthcheck確認済み。

今回は**第一段階のみ**: readiness APIと表示・ボタン可否。永続ジョブDB・idempotency・
反映後の再検証接続は**P1-2(次の単位)に送る**。

## やること

### 1. 新規 `app/workflow_readiness.py`
設計書 第4.1節のJSON構造どおりのレスポンスを組み立てる関数を実装する:
```json
{
  "project_id": "...", "goal": "...", "plan_version": 25, "plan_signature": "...",
  "mission_status": "...", "phase": "unverified", "state": "...", "state_label": "...",
  "stop_reason": "人向け1文", "provisional": true, "final_completed": false,
  "next_action": {"id": "...", "label": "...", "endpoint": null},
  "allowed_actions": {"prepare": {"allowed": true, "reason": ""}, ...},
  "blocked_actions": [{"id": "...", "reason": "..."}],
  "active_job": {"id": "...", "kind": "...", "updated_at": 0},
  "artifact_class": "none|provisional|final",
  "vehicle": {"applicable": true, "prepared": false, "unresolved_reads": 0,
              "unresolved_allocations": 0, "controls": "matched|mismatch|unavailable|empty"},
  "revision_token": "hash"
}
```
- `phase` は設計書 第4.1節の優先順位1〜10(running→正確性ブロッカー→fact_confirm→dev_blocked→
  issues_open→waiting_budget→unverified→provisional→complete→idle)で決める。
- **「確定完了」(`complete`)は、`goal_failures`が空 かつ 単位2Cで実装した照合検査(matched)が
  条件のときだけ**出す。P0実装前の誤表示を避けるため、この遅延バインドを厳密に守ること。
- 既存判定(`goal_review.execution_gate()`、`goal_review_queue`、単位2Cの`source_reconciliation_report`)を
  再利用し、UI側やこの新モジュール側で合格判定を再実装しない(既存関数を呼ぶだけ)。
- 未実装のaction(TRIZ採用再実行、レシピ適用)は`allowed_actions`に出さないか、`blocked_actions`で理由固定。

### 2. `app/web.py` にAPI追加(部分追加、全体書き換え禁止)
- `GET /api/projects/{id}/workflow-readiness` を追加。既存の `mission`、`goal-review`、
  `vehicle-profit` エンドポイントは変更しない(互換維持)。

### 3. ジョブ(第一段階の最小、設計書 第4.3節)
- 新規ジョブDB等は作らない。既存の `planning_projects` と review store の `status=running` を
  `active_job` に写すだけ。
- 二重送信防止: サーバーが実行中なら409を返す(既存の仕組みがあれば流用)。

### 4. UI(設計書 第4.4節、最小限)
- `app/static/goal_review.js` または `app/static/artifact_shelf.js` に、画面先頭へ
  目標・計画版・主な停止理由・次の操作・暫定/確定を表示する要素を追加する
  (新規 `app/static/workflow_readiness.js` に分離してもよい)。
- ボタンのdisabledは、毎回 `allowed_actions` から設定する(action終了時に一律有効化する現行方式をやめる)。
- 表示中かつ `active_job` または `waiting_budget` または `running` のときは3〜5秒間隔で
  readinessのみ再取得。通常は15秒でもよい。`document.hidden`なら停止する。
- 通信失敗は「処理失敗」ではなく「状態取得失敗」として扱い、再取得可能にする。

## テスト
設計書 第4章「受入条件の検証方法」1〜6を `tests/test_workflow_readiness.py`(新規)に実装:
1. 車両計画v24相当(全工程pending、plan_review null、goal_review required)→ phase=unverified、
   next_actionが修正案または外部検証、startはblocked
2. revision.blockersあり → dev_blocked、applyとstartがblocked
3. waiting_budgetをstoreに書いてGET → 待ちとnext。tick後のGETでphase変化
4. 車両inputがneeds_review相当 → artifact_class='provisional'、completeにしない
5. 未実装actionのIDがallowed_actionsに出ない
6. サーバーは200/4xxを混ぜない契約を守る

フロントJSは既存どおり `node --check` で構文確認する程度でよい。DOM試験・人手受入は今回不要。

## 制約
- 計画の構造修正(指摘対応など)はP1-2。配賦モデルはP1-3。今回は範囲外。
- `pytest -q`(プロジェクト全体)を実行し、実測結果を報告する。
- 実装前に、変更するファイル・関数・APIの一覧を示し、承認を得てから進める。
- 実行していないことを「できた」と書かない。
- **無関係な既存関数の調査に長時間はまり込まないこと。** 分からない点は、いったん保守的な
  仮実装(理由文言を汎用的にする等)で進め、テストが通ることを優先する。
- 完了後、変更内容と試験結果を日本語で要約する。
