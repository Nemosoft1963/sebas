## 0. 結論

1. **方向性は3社とも一致しており、正しい。** 部品は揃っており、欠けているのは制御層。順序は「GoalContract → 被覆表 → Completion Gate → 状態機械 → 次アクション制御(NAC)」。OCR改善・モデル交換は対象外。
2. **Grokの第1段階は骨格として採用できる。既存テストの退行もない。** ただし「暫定成果物を achieved にしない」という核心の保証には、いま3つの穴がある（第3章 F1〜F3）。この穴を塞ぐ前に第2段階へ進むと、NACが「穴のあるGate」を頼りに自動で動くことになり危険。
3. **よって計画は「第1.5段階（硬化）を新設し、Gateを本物にしてから完走制御へ進む」とする。** flag は車両案件のみONを維持し、全案件一斉ONはしない。

## 3. 第1段階実装のレビュー（コードで確認した欠陥）

重要度は「目標達成の誤判定・停止につながるか」で付けた。

### F1【重大】人間の確定（accept）が永続化されず、achieved に到達できない

- `completion_gate.evaluate()` の `accepted` は引数のデフォルトが `False`。`GET /completion-gate` も、`workflow_readiness` の内部呼び出しも `accepted` を渡さない。
- `accept()` は「確定OKなら評価行を1件保存する」だけで、承認そのもの（誰が・いつ・どの版に対して）をどこにも残さない。
- 結果、`canonical_state='achieved'` は API 経由では実質到達しない。
- 反対側の問題として、承認が契約hash・計画署名・入力/成果物hashに結び付いていない。設計書§13「入力版が変わった旧承認を流用しない」と、Gate条件7「承認は版に結合」を満たさない。
- 設計書のテスト GT-02（条件を満たし承認済みなら achieved true）が実装されていない。今のテストは「achieved にならない」側だけを確認している。

### F2【重大】Gateの車両判定が「失敗メッセージの日本語部分一致」に依存し、PASSは「不在証明」でしかない

- `_map_vehicle_failures()` が `goal_failures()` の文言（「未確認・未配分・未照合」等）を部分一致で条件IDへ振り分けている。文言を1文字直すと別条件に紐づく、またはどこにも紐づかない。
- `goal_failures()` が空のとき、C01〜C12 は全て自動的に PASS になる。C06（リース税込注記）や C03（費目定義）には専用の検査が無い。「失敗が出なかった」ことを「条件を満たした」ことにしている。
- 逆にメッセージが1件でもあると、紐づかなかった全条件が FAIL になり、どの条件が本当に止まっているかが分からない。
- 変更履歴の `goal_failure_records` は「構造化」をうたうが、中身は同じ文字列マッパーを呼び返すラッパーで、`vehicle_workflow` と `completion_gate` の循環参照になっている。設計書§4.2の意図（失敗を構造化して返す）は満たされていない。

### F3【中】計画被覆表が「計画が条件を閉じるか」を見ていない

- 車両では、条件→タスク種別の固定写像で埋まり、verify 側は「`final_verification` か `vehicle_verify` を持つ任意のタスク」に自動割当される。つまり実質的に落ちない。
- テスト `test_flag_blocks_approve_when_coverage_forced_empty` は、契約を手で壊して不合格にしているだけで、実際の計画の穴を検出する試験ではない。設計書の CV-02（verifyだけの条件は承認拒否）に相当する試験もない。
- `build()` 内に、何もしない `pass` だけの分岐（exec と verify が同一タスクの検査）が残っている。

### F4【中】flag OFF でも生成経路に書き込みがあり、フェイルオープンになっていない

- `after_generate()` は flag OFF でも毎回、契約ドラフトと被覆表を書く。この呼び出しは try/except で保護されていないため、別SQLiteのロックや書込失敗で **既存の `generate_plan` が失敗する**。「flag OFF なら現行の挙動は変わらない」という保証が完全ではない。
- `build_readiness()` が呼ばれるたびに Gate（`goal_failures` と原本照合）を再計算している。進行パネルのポーリングごとに重い処理が走り、例外は握りつぶされる（ログなし）。

### F5【中】契約hashに原本・入力の版が入っていない

- 設計書は `source_versions` に原本hash・OCR採用版・入力hashを含めるとしているが、実装は `mission_plan_version` と `vehicle_engine_revision` のみ。
- 原本が差し替わっても契約側は変わらず、HASH_DRIFT は `goal_failures` の文言頼みになる。F1の承認結合にも直結する。

### F6【軽微】未使用のテーブルと状態

- `goal_states` テーブルは作成されるが誰も使っていない。`canonical_state` は readiness 内の辞書写像で、遷移履歴が残らない（第2段階の範囲なので欠陥ではないが、UIに出す以上「履歴なし」と認識しておく）。
- `complete` → `achieved` の写像は F1 のため到達しない。

### 良い点（維持する）

- 既存 phase 名・テストを壊さない足し算の設計。
- 暫定Excel・`mission completed` だけでは achieved にしない方針が、コードでも明示されている。
- 未配賦分類 `classify_unresolved` は0円埋めをしない設計で、テストもある。
- flag が案件単位で、既定オフ。

## 4. 改修計画

進め方の原則: **①既存を壊さない足し算 ②Gateが本物になってから自動化する ③各段階でflagを切れば旧挙動に戻る ④本番投入・flag ONは専務の承認**。工数は「Claudeが開発側で実装・試験する作業量」の目安で、本番反映の待ち時間は含まない。

### 第1.5段階: Gateの硬化（最優先・第2段階の前提）

目的: 「achieved は本物のときだけ」を、コードとテストで保証する。

| # | 作業 | 対応する欠陥 |
|---|---|---|
| 1 | **承認台帳 `human_acceptances` を新設**。列: project_id / contract_hash / plan_signature / input_hash / artifact_hash / accepted_by / accepted_at / note。`accept()` はここへ記録し、Gate条件7は「現行の各hashと一致する承認行があるか」で判定。`evaluate()` の `accepted` 引数は廃止。承認は `goal_state_events` にも記録 | F1 |
| 2 | **hash変化で承認を自動失効**。契約・計画・入力・原本・Excelのいずれかが変われば承認は無効 | F1, F5 |
| 3 | **契約hashへ原本hash・入力hash・OCR採用版を追加**（車両のみ必須） | F5 |
| 4 | **`goal_failures` を構造化して返す層を作る**。文字列でなく `{code, criterion_ids, evidence_path}` を検査側が直接返す。`_map_vehicle_failures` と循環参照は廃止し、旧 `goal_failures()`（文字列配列）は互換のため残す | F2 |
| 5 | **条件ごとの正の検査を追加**。C06（税込注記）、C03（費目定義）、C08（車両別シート数）、C01（対象確定）など、専用検査が無い条件に実検査を書く。「失敗が空だからPASS」を禁止し、`PASS` には必ず検査ID・証拠パスを付ける。検査が未実装の条件は `UNTESTABLE` とし、achieved を出さない | F2 |
| 6 | **被覆表を実計画ベースに**。verify は「その条件に紐づく検査ID」を持つものだけを有効とし、任意の最終検証タスクへの自動割当をやめる。verify のみ/exec のみは不合格 | F3 |
| 7 | **flag OFF 経路をフェイルオープン化**。`after_generate` を try/except で保護し、失敗時は警告ログを残して従来どおり動く | F4 |
| 8 | **readiness のGate評価をキャッシュ**（キー: 契約hash+計画署名+入力hash）。例外は握りつぶさずログ出力し、`gate.error` として画面へ返す | F4 |
| 9 | **未使用の `goal_states` は第2段階まで作らない**（または第2段階で実装するまで削除） | F6 |
| 10 | **現状値の計測を入れる**（車両案件の自動完走率・質問数・再停止回数）。METAの数値目標の根拠にする | 比較表 |

追加テスト（設計書の未実装分を含む）:

- GT-02: 全条件PASS＋現行hashに結合した承認 → `achieved=true`
- GT-04: 承認後に入力または原本のhashを変更 → 承認失効、`achieved=false`
- GT-05: `goal_failures` が空でも、検査未実装の条件があれば `achieved=false`
- GT-06: 失敗文言を書き換えても、条件への紐づけが変わらない（文字列非依存の確認）
- CV-02: verify のみ/exec のみの条件がある計画は承認拒否（実計画で確認）
- FL-01: 別SQLiteを書込不能にしても、flag OFF の `generate_plan` は成功する
- WR-03: readiness を連続呼び出ししても Gate 再計算が1回に収まる

完了条件: 既存テスト 657 件が維持され、上記が全て通ること。暫定成果物・`mission completed` のみ・承認なしの3ケースで achieved が出ないこと。承認を記録した完全ケースでのみ achieved が出ること。

目安: 中規模（1〜2セッション）。

### 第2段階: 完走制御（状態機械＋NAC）

前提: 第1.5段階完了。

1. `goal_state_machine` を実装し、`goal_states` / `goal_state_events` を正本にする。旧 `mission.status` は書き続け（dual write）、読取時に写像する。不正遷移は拒否。`achieved` の直接書換を禁止。
2. `next_action_controller` を実装する。`GET /next-action`（計算のみ）と `POST /next-action/execute`（冪等キー付き）。class が `human_*` / `external` なら 409。
3. 自動連鎖は `local_safe` のみ、最大5回、`RecoveryBudget`（LLM3/ツール6/サイクル2/300秒）を project+criterion で共有。同一actionの連続実行は禁止。暴走時は `needs_approval` へフォールバック。
4. 「既回答36項目の適用」を `local_safe` actionとして接続。ただし適用は `subject_key＋期間＋入力版` が一致した場合のみ。金額の一般化はしない。
5. `workflow_readiness` の未実装操作（triz_adopt / triz_rerun / recipe_apply）は、Controllerの `blocked` に統合。TRIZ adopt は既定拒否を維持。

完了条件: 車両案件で、承認と未配賦入力の箇所でだけ停止し、それ以外は人手なしで連鎖する。再開後に同一原因で3回以上止まらない。

### 第3段階: 証拠と回復

1. `evidence_graph`（車両×月×費目 → 原本ページ/行）。車両損益のみ必須、他分野はサンプリング。ノードは遅延生成。
2. 最小質問UI（不明点／止まる条件／確認済み事実／候補と影響／再実行範囲）。1質問最大5件。回答は版付き `facts` へ保存。
3. 汎用案件の要求保持: LLM分解（`/goal-contract/decompose`、保存しない）＋原文対応表＋人間は「削除・統合のみ」確認。汎用案件の achieved は当面 `verified` 止め。
4. 再起動時、残留 `running` ジョブを成果物・lock・checkpoint と照合して収束させる。
5. `automatic_triz` の入口で `SOURCE_*` / `ALLOCATION_*` / `FACT_MISSING` / `DEVELOPMENT_REQUIRED` を発明対象から除外。

### 第4段階: 車両基準シナリオの完全受入

1. 稼働案件「車両別評価データの作成」（plan v25、未配賦225件）で、12条件を全て独立に検査。
2. 未配賦の分類→既回答適用→残件のみ最小質問。
3. 受入条件: 全車両・全月、未解決0、独立照合PASS、人間確定済みのときだけ achieved。暫定Excelは produced のまま。

### 第5段階: 整理と観測

`CURRENT_SYSTEM_STATE.md/.json` の機械生成、release manifest（Git導入含む）、指標ダッシュボード、旧 `completed` 表示の縮小。UIの5画面化はここで行い、それまでは既存進行パネルへ追加表示に留める。

## 5. 設計判断（Claudeの決定）

1. **永続化は別SQLite方式を維持する。** ただしバックアップ・healthcheck の対象に `goal_completion.sqlite3` を必ず追加する（第1.5段階に含める）。
2. **既存APIの破壊的変更はしない。** 新機能は追加フィールド・追加ルートで提供し、旧クライアントは無変更で動くこと。
3. **Gateの判定は「正の証拠」方式とする。** PASS は検査IDと証拠を伴うときだけ。証拠が無い条件は `UNTESTABLE` で、achieved を止める。
4. **人間の承認は版に結合する。** 版が変われば自動失効し、承認を書き換えるのは人間のみ。Claudeが代理で approve / accept / RAG verified を書くことはしない。
5. **計画署名へ `contract_hash` を入れる時期は第2段階。** 第1.5段階では署名計算を変えない（外部AI検証の再実行を避けるため）。
6. **数値目標（自動完走率80%など）は、現状値を計測してから確定する。**

## 7. 安全境界（実装時の遵守事項）

- Docker・Ollamaモデル・履歴・原本・既存DBの初期化はしない。`docker system prune` 系を scripts に足さない。
- 原本・個人情報・会計情報・認証情報を外部packetに載せない。外部送信・公開は人間承認。
- 未確認の金額・料率・配賦を推測しない。0円埋めをしない。
- 暫定Excelを確定成果と呼ばない。TRIZ候補の生成を業務回復と表示しない。
- 各段階の完了時に `scripts/healthcheck.ps1` を通し、BUILD_REPORT に「開発側で確認・本番未実証」と明記する。
- ロールバックは flag OFF。新テーブルは残してよく、mission・計画・車両成果物には触れない。
