## 1. P0-1 金額の欠損・読取失敗・実額ゼロの分離

**採用: 両案を統合。原因分析はGROK版、結果型はChatGPT版のdataclass、`text()` 非改変と数式キャッシュ経路の維持はGROK版。**

### 現状再確認

提案・再監査の中核は現行コードと一致する。未修正。

原因の連鎖:

1. `app/vehicle_auto.py` `text()`（16–17行）: `str(value or '')`。数値 `0` は falsy なので空文字になる。`False` も同様。
2. `money()`（24–31行）: 空は正規表現不一致で `None`。文字列 `'0'` / `'0.0'` は 0 を返す。よって **数値0は欠損扱い、文字列0は実額**。絶対値が `1e12` 超は `None`（範囲外）。
3. `Extractor.add()`（122–139行）: `amount is None` のとき、数式キャッシュ欠落（`formula_gaps`）なら `kind='read'` を出すが、**通常の非数値・空・数値0由来の None は return するだけ**。明細も確認事項も残さない。
4. `finish()`（315–331行）: `zero=True`（案件文に「不足…0円」があるとき `authorized_zero()`）なら、配賦済み実額の無い車両×月×費目へ `quality='assumed_zero'`、`source_ref='policy:missing-zero'` を補う。黙って捨てた読取失敗も「対象明細なし」と見なされ仮定0円になる。
5. `evidence_issues()`（393–400行）: 未解決 issue と仮定ゼロ方針と原本参照だけ。読取失敗が issue に無い限り検証を通す。
6. `vehicle_profit.calculate()` は `quality` を `actual|estimated|missing|assumed_zero` に限定。読取失敗用の区分が無い。

CSV燃料だけは例外で、金額欄が `None` なら issue を出して continue する（240–243行）。Excel台帳・給与・汎用台帳は黙って捨てる。経路で品質が違う。

数式セルのキャッシュ無しは `formula_gaps` で issue 化済み（`tests/test_vehicle_auto.py` `test_formula_without_cached_value_is_not_silently_treated_as_absent`）。これは維持する。一方、非数式の「要確認」や数値0は既存試験が検出していない、という再監査の指摘は現行試験でも正しい。

`triz_common.validate_problem` の None 修正は本不具合と無関係（変更確認どおり）。

古くなっている点: 再監査が `money` 単体の16行を根拠にしたこと。本質は `text()` の falsy 変換。`money` だけ直しても、他が `text(0)` を使うと同じ罠が残る。

### 設計方針

金額の解釈結果を相互に変換しない。分類は次の4つ（業務上の意味はGROK版、型はChatGPT版）。

| 分類 | 入力例 | 保存 | 不足0円方針 | 確定完了 |
|---|---|---|---|---|
| 実額（非ゼロ） | `1000`, `'1,000円'` | `quality='actual'`, amount=整数 | 適用しない | 他条件次第 |
| 実額ゼロ | `0`, `'0'`, `0.0` | `quality='actual'`, amount=0, 原本セル参照必須 | 適用しない | 他条件次第 |
| 真正の欠損 | 空セル、空白のみ | レコードを作らない。当該車両×月×費目が空なら不足0円方針時のみ `assumed_zero` | ここだけ適用 | 方針無なら未確定 |
| 読取失敗 | `'要確認'`, `'—'`, 非数値、計算値の無い数式、範囲外、真偽値 | 明細に入れない。`issues` に `kind='read'`、原本セル・生値・理由 | 適用しない | 阻止 |

#### 1.1 金額読取結果を型付きで返す

**ChatGPT版のdataclassを採用。** dictより型と試験が安定し、呼出し側のキー打ち間違いを減らせる。

```python
@dataclass(frozen=True)
class MoneyParseResult:
    status: Literal['value', 'blank', 'invalid', 'out_of_range']
    amount: int | None
    raw_text: str
    raw_type: str
    reason: str = ''


def parse_money(value) -> MoneyParseResult: ...
```

分類規則:

- Python の `int` / `float` / `Decimal`（**`bool` 除外**）は文字列化せず数値として扱う。`0` は `status='value', amount=0`。
- 文字列は現行のカンマ・円・¥除去のあと、空なら `blank`、正規表現不一致なら `invalid`。`'0'` / `'0円'` は `value, 0`。
- `None`、空文字、空白だけ: `blank`。
- 絶対値 `1e12` 超、NaN: `out_of_range`（現行 `money()` の範囲外を明示化。ChatGPT版は `invalid` に畳む案だったが、既存の範囲検査を消さないため分離する）。
- 真偽値: `invalid`。0/1として扱わない。

**採用しない細部と理由:**

- ChatGPT版の `status='formula_missing'` と `parse_money(..., formula_missing=True)` は採用しない。数式キャッシュ欠落は現行どおり `formula_gaps`（セル座標単位）で検出し、`add()` 側で `kind='read'` にする。パース関数に原本セル状態を混ぜると、CSV・PDF経路が偽の引数を持つことになる。
- GROK版の dict 戻り値は採用しない。意味は同じだが dataclass の方が保守性が高い。
- GROK版の `status='amount'|'unreadable'` という語彙は、ChatGPT版の `value` / `invalid` に合わせる（後続の Reconciliation / Adapter 文書と揃える）。業務分類表の「実額／読取失敗」という言い方はそのまま使う。

互換性のため `money()` を直ちに全面削除せず、内部で `parse_money()` を呼んで `status == 'value'` の金額だけを返す薄い関数にできる。ただし抽出器は必ず `parse_money()` を使用し、黙って `None` を返す経路を残さない。

#### 1.2 `text()` は当面維持する

**GROK版を採用。** ChatGPT版は `text()` を「`None` だけ空文字、数値0は保持」へ変える案だが、氏名・車番・会社判定にも使う。金額経路を `parse_money` が `text()` を通さない形で先に分離する方が影響範囲が小さい。金額以外で `0` を空にする害は小さい。将来 `text()` を直す場合は、氏名・車番の回帰を別単位にする。

#### 1.3 抽出明細と読取問題の保存

**GROK版の既存 `issues` を拡張する案を採用。** ChatGPT版の並列配列 `read_failures` と schema `vehicle-profit-input-v2` 一斉切替は、移行期間の二重管理コストが大きい。読取失敗は現行 `auto_extraction.issues` の `kind='read'` に、ChatGPT版が求めた機械可読フィールドを載せる。

```python
# issues 要素の拡張（既存キーは維持）
{
  "id": "...",
  "kind": "read",                 # 既存
  "source_ref": "context:...",
  "locator": "Sheet!C12",
  "message": "...",               # 人向け
  "status": "unresolved",
  "raw_text": "要確認",
  "reason_code": "non_numeric",   # non_numeric | formula_missing | out_of_range | boolean
  "month": "2026-01",
  "category": "fuel"
}
```

`Extractor.add()` は ChatGPT版のように `parsed: MoneyParseResult` を受け取る形へ変更する（呼出し側の分岐漏れを防ぐ）。内部規則:

- `value`: 現行どおりレコード。`amount==0` でも `quality='actual'`、`source_locator` 必須。
- `blank`: レコードも issue も作らない（真正欠損。finish の不足0円が判断）。観測として `(vehicle候補, month, category)` を内部に残してよいが、確定用レコードにはしない。
- `invalid` / `out_of_range`: `issue('read', ..., raw_text=..., reason_code=...)` して return。レコードを作らない。
- 数式キャッシュ欠落: 現行どおり `formula_gaps` を見て `reason_code='formula_missing'` の read issue。

`if not allocations and amount:` はゼロ円でも配賦不要（帰属先が1台なら既存どおり ratio=1）。複数候補で0円のときは issue を出すか（業務確認、第13章）。

CSV燃料: 既に unreadable を issue 化している。`parse_money` 導入後も同様。空欄行は blank としてスキップし、0円行は実額ゼロ。Excel台帳・給与・汎用台帳も同じ関数に揃える。

#### 1.4 仮定ゼロの適用条件

`finish()` の0円補完は「actual 明細がない」だけでは足りない。

- 同じ車両×月×費目に未解決 `kind='read'` がある場合は補完しない。
- 同じ費目に未配賦 record がある場合は、そのキーを「対象明細なし」と見なさない。
- 読取失敗・未配賦・照合不能は0円で解消しない。
- 適用した場合は `zero_reason_code='authorized_missing'` と要求ハッシュを保存する（ChatGPT版）。既存試験 `test_automatic_ledger_no_manual_json_and_zero_policy` が「空の費目→仮定ゼロ」を期待しているので、**真正欠損のみ** に限定して残す。

`vehicle_profit.calculate()` に新 quality を増やさない。読取失敗は records 外の issues に置く（GROK版。算術エンジンを壊さない）。Excel「不足と未配賦」は既に `auto_extraction.issues` を出しているので、欠損・読取失敗・数式未計算・未配賦・仮定ゼロを別表示する（ChatGPT版の表示方針）。

REVISION を上げる（例: `20260923.1`）。`prepare()` / `execute()` は extractor_revision 不一致で再抽出する既存機構を使う。入力 schema は当面 `vehicle-profit-input-v1` のままフィールド追加し、破壊的な v2 一斉切替はしない。

### 受入条件の検証方法

合成Excel（openpyxl、キャッシュ値付き）とCSVで、同一抽出器に対し次を **1試験1主張** で追加する。

1. **数値0:** 売上セルに Python int `0`。レコード `quality='actual'`, `amount=0`、`source_locator` あり。`assumed_zero` にならない。`issues` に当該セルの read が無い。
2. **文字列0:** `'0'` も同様に実額ゼロ。
3. **空欄:** 対象費目が空。方針オフなら利益 `None`（既存 `test_no_silent_zero_without_authorization`）。方針オンならその費目だけ `assumed_zero`。
4. **非数値「要確認」:** 燃料費セル。`issues` に `kind='read'`、locator がセル座標、生値または `reason_code` を含む。`amount=0` の actual/assumed_zero を作らない。`evidence_issues` が空にならない。`validate_evidence` 自動経路が失敗する。
5. **計算値のない数式:** 既存試験を維持。仮定ゼロにしない。
6. **再現ケース解消:** 売上1000・燃料「要確認」・不足0円方針オン。燃料が無警告で0円確定にならない。計算は暫定になり得るが `status='completed'` 相当の検証（`checks['source_controls']` や `evidence_issues==[]`）を通さない。
7. **回帰:** 既存 ledger 試験、CSV符号付き金額、数式、重複CSV/PDF（P0-3前は現行期待のまま）。真偽値を0/1にしない。範囲外は invalid/out_of_range でレコード化しない。

#### 2.1 原本統制値

**ChatGPT版の「取得不能でも行を残す」を採用。** GROK版はオブジェクトを作らず issue だけにする案だったが、照合シートと監査で「なぜ合格でないか」を行として残す方が保守しやすい。ただし GROK版の拘束を残す: **明細を足した値を `origin='source_total'` として保存してはならない。**

```json

  "company": "関東",
  "month": "2026-01",
  "category": "fuel",
  "tax_basis": "inclusive",
  "invoice_id": null,
  "control_kind": "invoice_total",
  "origin": "source_total",

```

取得できない場合:

```json
{
  "source_ref": "context:...",
  "company": "関東",
  "month": "2026-01",
  "category": "fuel",
  "status": "unavailable",
  "origin": "none",
  "reason_code": "no_independent_total",
  "reason": "明細のみで請求総額欄がない"

```

#### 2.2 照合の純粋関数

**ChatGPT版を採用。** `app/vehicle_workflow.py` をこれ以上肥大させない。新規 `app/vehicle_reconciliation.py`。

```python
def reconcile_sources(
    records: list[dict],
    controls: list[dict],
    dispositions: list[dict],
    excluded_records: list[dict],
    read_issues: list[dict],
) -> list[dict]:
```

各キーで次を計算する。

- `source_total`: 原本統制額（`origin='source_total'` かつ `status='available'` のみ）
- `included_total`: 取り込み record 額
- `excluded_total`: 金額と根拠を持つ対象外額
- `unallocated_total`: 取り込み済みだが車両未配賦の額（included の内数として別表示）
- `unread_unknown`: read issue 等で金額不明なら数値化せず `unknown_components > 0`
- `difference = source_total - included_total - excluded_total`
- `status`: `matched | mismatched | unavailable | incomplete`

未配賦は抽出漏れではないため原本対取り込み照合では included に含めるが、車両損益確定ゲートでは別途阻害する。除外は金額、原本位置、理由、承認主体を持つ場合のみ差引可能とする。読取失敗が混ざるキーは `incomplete` であり、差額0でも matched にしない。

#### 2.3 確定ゲート

`validate_evidence()` の自動・手入力分岐を廃止し、共通検証へ統合する。

- 全対象 source に disposition がある。
- 必要な control が `available` かつ `origin='source_total'`。
- reconciliation が全件 `matched`。
- control のない対象は `unavailable` として明示され、確定不可。空配列を合格にしない。
- read_failure、未根拠除外、重複 control、対応明細なし control、`origin='sum_of_lines'` だけの control は確定不可。

チェックを真偽値だけでなく構造で保存する（ChatGPT版）。

```json
"checks": {

  "source_reconciliation": {
    "passed": false,
    "matched": 10,
    "mismatched": 1,
    "unavailable": 2,
    "artifact": ".../source_reconciliation.json"

}
```

互換用 `source_controls: bool` は、詳細チェックの `passed is True` からの導出に限り残す。空配列や issues 空からの True は廃止する。`execute()` 284行の代入は残してよいが、中身が空配列合格をやめる。`goal_failures()` は詳細チェックの `passed is True` のみを合格とする。

## 3. P0-3 請求単位の重複判定と部分抽出検知

**採用: ChatGPT版のデータ構造（InvoiceDocument / AdapterResult / 関係分類）を土台に、GROK版の現行アダプター挙動と既存試験の更新方針を拘束条件とする。**

### 現状再確認

提案どおり未修正。再監査は「コード上のリスク」であり、実原本の漏額は未確定、という但し書きもそのまま。

- CSVを先に処理し、キーを `csv_keys` へ。
- **`請求書(鑑)` を無条件 excluded**。または PDF かつ同一キーの CSV がある場合 excluded。
- 除外 evidence 文言は「照合参照として保持」だが、実際は dispositions のみで controls に載らない。

`fuel()` 戻り値は `len(self.records)>start`。1行でも読めれば成功。宇佐美PDFは `if not sub or not printed: continue` でブロックを黙って飛ばす（261–280行）。太陽・車番別集計もマッチ行だけ加算。

### 設計方針

#### 3.1 請求文書メタデータ

**ChatGPT版を採用。** GROK版の `invoice_identity` dict より、役割・完全性・fingerprint を一つの型に載せられる。

```python
@dataclass
class InvoiceDocument:
    source_ref: str
    vendor: str
    company: str
    billing_month: str
    invoice_number: str | None
    invoice_date: str | None
    printed_total: int | None
    detail_count_printed: int | None
    document_role: Literal['detail', 'cover', 'combined', 'unknown']
    detail_fingerprints: list[str]
    extraction_complete: bool
    extraction_issues: list[dict]
```

明細 fingerprint は、可能な範囲で `日付、車番、商品、数量、税、金額` の正規化値から作る。source ファイル名や行番号だけを同一性根拠にしない。請求番号が原本に無い形式は `invoice_number=None`。

#### 3.2 重複判定

```python
def classify_invoice_relation(a: InvoiceDocument, b: InvoiceDocument) -> Literal[
    'exact_duplicate', 'same_invoice_complement', 'different_invoice',
    'partial_overlap', 'unknown'
]:
```

優先規則:

1. vendor/company/invoice_number が一致し、printed_total と明細集合も一致 → `exact_duplicate`。後着は excluded。disposition に先行 source_ref。二重加算しない。
2. 請求番号一致、CSVとPDFが相補的で総額一致 → `same_invoice_complement`。明細精度が高い方を計上し、他方は control 証拠。
3. 同月でも請求番号が異なる、または同一業者・会社・月で指紋不一致 → `different_invoice` として **両方保持**。
4. 請求番号なしでも明細集合・合計が完全一致 → exact_duplicate 候補。ただし根拠を保存。業務確認（第13章）が未決の間は確定不可でも除外はしてよいが、根拠なしの自動除外はしない。
5. 一部だけ一致、合計差あり → `partial_overlap`。自動除外せず確定阻害。多い方を正、欠け側は照合待ち。
6. 比較不能 → `unknown`。二重加算を避けた暫定選択は可能だが、確定不可。除外しない（二重の恐れを隠さない）。

`source_dispositions` に `duplicate_of`、`relation`、比較した請求番号・総額・fingerprint 件数を保存する。

#### 3.3 請求書鑑を control として使用する

`document_role='cover'` は明細計上しないが、無条件の「重複除外」ではなく、請求総額 control として P0-2 へ渡す。明細CSV/PDF合計と鑑総額を照合し、差額を保存する。

#### 3.4 部分抽出

`fuel()` の bool 成功を廃止する。

```python
@dataclass
class AdapterResult:
    matched: bool
    records_added: int
    parsed_total: int
    printed_total: int | None
    expected_detail_count: int | None
    parsed_detail_count: int
    complete: bool
    issues: list[dict]
```

`complete` は少なくとも次のいずれかを満たす場合のみ true。

- 明細数と総額が原本表示と一致。
- 総額のみ存在し、抽出明細合計と一致し、未解析領域がない。
- vendor 固有の終端・ページ・小計検査をすべて通過。

1件でも読めた、という条件だけでは complete にしない。`extract()` が complete でない PDF を csv_keys の除外条件に使わない。

宇佐美: ブロック検出数を expected とし、sub/printed 欠落を issue。太陽・車番別: 小計行の合計と明細加算の差を control。

これらの型は `vehicle_auto.py` に置いてよい。関係分類と control 集約が膨らむ場合は P0-2 の `vehicle_reconciliation.py` へ寄せる（ChatGPT版）。循環 import を避ける。

### 受入条件の検証方法

1. **同月別請求:** 同一会社・月・宇佐美で合計も明細も異なるPDF/CSV 2件。レコードが両方残る。excluded にしない。

- 車両自動抽出・確認事項は別 `details`。計画の外部検証待ちと一つの進行状態にならない。
- 仮定ゼロ件数・未配賦は出すが、暫定/確定の語は成果物メタの「現行計画 / 目標未達」程度。
- **`GET /api/projects/{id}/workflow-readiness` は無い。**
- 長時間処理の永続 job_id がAPIに無い。`web.py` のグローバル `executions` はメモリ上。

古くなっている点: 指摘取込・修正案・反映・外部検証の **操作自体は既にある**。足りないのは統合状態とジョブ追跡。新API名 `workflow-readiness` は未存在であり、既存APIと混同しないこと。

### 設計方針

指摘を「文章」「契約」「開発」に三分し、実行条件を迂回しない。

#### 5.1 対応表

既存キーは維持し、ChatGPT版の target/patch と GROK版の binds を両立できる形にする。

```python
{
  "issue_id": "...",
  "disposition": "amend|rebuild_vehicle|development|business_fact|unresolved",
  "target": "...",
  "change": "...",
  "reason": "...",
  "targets": [
    {"type": "goal|task|dependency|contract|verification", "id": "vehicle_calculate"}
  ],
  "binds": {
    "goal_criterion_ids": ["SC01"],
    "task_key": "vehicle_extract",
    "contract_patch": null,
    "test_ref": "tests/test_vehicle_auto.py::test_..."
  }
}
```

disposition 意味:

- `amend`: 説明追記 **かつ** 契約を変えない確認手順の具体化。専用器の動作は変えない（現行強制を維持）。
- `rebuild_vehicle`: 現行どおり、抽出工程欠落の旧計画のみ。**現行4工程への再構成は禁止**（二重計画）。車両計画は `make_plan()` の決定論的再生成を優先。
- `development`: P0/P1-3/P2 のコード欠落。`test_ref` または受け入れ条件文。apply 不可。start 不可。文章 patch で解消しない。
- `business_fact`: P1-3 の所属・乗替等。コード欠落ではない。
- `unresolved`: 根拠不足。

**初期実装に入れないもの（GROK版）:** `contract_fix` / 任意の契約パッチ。車両の正確性はコード改修（P0）であり指摘反映では閉じない。ChatGPT版の許可リスト方式（description/objective、`depends_on`、verification）は、validator を別単位で足す場合の拡張口としてスキーマに `targets` を予約するに留める。不合格 patch を保存・適用しない。

#### 5.2 指摘ライフサイクル

**ChatGPT版を流れの定義として採用する。** 「文章に追加した」だけで validated にしない。

```text
imported -> classified -> proposed -> applied -> revalidation_pending
-> validated | rejected | development_pending | business_fact_pending
```

解決条件は、新 plan_signature に対する外部検証結果、対応したテスト/契約、または明示された業務事実回答とする。

#### 5.3 オーケストレーションとジョブ

次の段階を一つの workflow として管理する（ChatGPT版）。外部送信は step 6 なしに自動遷移しない。

1. feedback import
2. local proposal
3. human confirmation
4. apply
5. public packet regeneration（`public_draft()` で再生成してフォームへ入れる。自動送信はしない）
6. explicit send approval（packet hash、provider 一覧、公開用本文を承認記録へ）
7. external re-review / budget queue
8. plan human approval
9. execution start

反映後の計画へ古い plan_review を流用しない（署名が変わる既存仕様を維持）。plan/source/requirements hash が変われば step 5 へ戻す。

ジョブ: この単位で ReviewStore の `kind='job'` または共通ジョブ表を導入する。`propose` / `review_plan` / `prepare` 開始時に id を返し、GET readiness が拾う。同じ idempotency_key の running/succeeded があれば二重実行しない。外部送信済みか不明なクラッシュは自動再送せず `needs_attention`（既存 `goal_review_queue` の安全策を維持）。再読込で generating/running を復元。二重は 409（review_plan の240秒ガードを一般化）。

再開位置: `next_action` が「修正案再生成」「公開文確認」「検証送信」「承認」「実行」「車両確認」のいずれか。部分失敗は最後の applied 署名と現行署名の差で案内。`last_completed_stage` と `blocking_error` を保存する。

未解決開発課題があるときの部分保存: 対応表の draft 保存は現行どおり可。apply と execution_gate は blockers で止める。安全な説明修正だけ通す場合も、車両専用器の実行条件は解除しない。

## 6. P1-3 月別配賦・社会保険根拠・判断継承

### 設計方針

#### 6.1 割当レコード

**ChatGPT版の AllocationRule を目標構造とする。** GROK版の month 文字列だけでも段階導入は可能だが、月中乗替の業務確認が「日付」になったときに壊さない。

```json
  "effective_from": "2026-01",
  "effective_to": "2026-07",
  "allocations": [
    {"vehicle_id": "...", "ratio": "0.6"},
    {"vehicle_id": "...", "ratio": "0.4"}

  "basis_type": "work_days|mileage|manual_business_fact|source_explicit",
  "basis_evidence": "context:... Sheet!A1",
  "reason": "...",
  "source_hash": "...",
  "created_by": "human|source_rule",
  "decision_id": null,
  "status": "active"

```

初期実装の期間粒度は **月**（GROK版）。日付が必要かは第13章の未決。未決の間は確認へ回し、一括配賦しない。ratio 合計1、会社整合、期間重複を validator で検査する。合計1超は 422。

`payroll` add: その月に有効な assignment が1件ならその車両100%。複数なら指定 ratio（合計1）または確認。0件なら現行どおり allocation issue。**グループ全月を一括で1台にしない。**

#### 6.2 decide()

対象を「group 全件」から「明示された issue_id と、同じ employee×month の明細」へ。全月一括は `apply_to='this_month'|'date_range'` をクライアントが送る（既定 `this_month`、GROK版）。複数車両: `allocations: [{vehicle_id, ratio}]` をAPIで受け、合計1をサーバー検証。保存時に assignment を追加。UIでは月別行を展開する。

#### 6.3 判断継承

再抽出時に旧判断を無条件再適用しない。

1. history の decisions/assignments を読む。
2. subject key が同じ、対象月が有効期間内、vehicle ID と会社が現行対象集合に存在、根拠 source の hash が同じ（または原本変更後も再確認済み）。
3. 両立するものだけ allocations に再適用（`reused`）。不成立は unresolved に戻し、理由 `stale_decision` / `needs_revalidation` / `invalid`。
4. 人間への質問は、原本で解決不能な所属・乗替・算定条件に限定（読取失敗は P0-1 でシステム側）。

#### 6.4 社会保険

- 明示列があるときだけ取り込む（現行）。
- 列が無い・読めないときは issue `kind='insurance_basis'`。「料率×給与」で埋めない。
- 本人控除列（例: 社会保険料、健康保険料の個人負担）を insurance にマップしない。列エイリアスを **拒否リストで固定**（GROK版）。
- 算定条件が必要な場合は確認UIに「根拠額のセル」または「対象外」だけ出す。
- ChatGPT版の `insurance_basis` 構造は、明示額の locator 保存に使う。`calculated_from_confirmed_rule` は業務仕様が揃うまで実装しない。

```json
"insurance_basis": {
  "kind": "explicit_employer_amount",
  "source_refs": [],
  "rule_version": null
}
```

#### 6.5 仮定ゼロ整理

同一車両×月×費目に `actual` が付いたら、そのキーの `assumed_zero` を削除する正規化関数を作る。削除履歴は decision log へ残す。未配賦 actual があるだけでは全車両の zero を自動削除せず、配賦確定後に行う。P0-1 後に実施。

### 受入条件の検証方法

1. **乗替:** 同一社員、1–3月車両A、4–7月車両B。給与が月ごとに分かれる。一括Aにならない。
2. **複数配賦:** 人間が 0.5/0.5（または 0.6/0.4）を保存。calculate が両車両に配分、未配賦0。合計1超・0以下・会社不一致・期間重複は 422。

- grep で「本番未投入」が TRIZ CHANGELOG の最新節に残らない。

- BUILD_REPORT に 403 と 434 が **別日付の項** として共存し、混同注意がある。全体未実行の focused test を全体合格と読めない。
- コード差分が文書以外に無いこと（単位0）。
- 旧ZIPの manifest に現行との差分と一括復元禁止が明記される（単位9）。

### 依存関係

なし。実施順序1の保全と並行してよい。最終件数・新再開記録は各実装単位のテスト後に更新する。配備やDB変更を行わない今回の設計段階では、現状不一致の記載に留める。

## 11. 実装単位に分割した実行計画

**採用: 両案を統合。単位番号はGROK版の0–9を骨格にし、単位2の2A/2B/2Cと単位9のマニフェストはChatGPT版。**

提案書の実施順序1〜5に沿い、P0を最優先。1単位 = 1つの実装セッション（または1PR）で完結できる範囲。コード変更は本設計の範囲外。各単位は原則として前単位のテストを通してから次へ進む。

### 単位0 — 保全と記録（順序1 + 記録の同期）

範囲:

- 現行計画・キュー・vehicle input・extractor REVISION・review store・TRIZ store・recipe・Workspace 成果物の読み取り確認（起動せず、ファイル/DBコピー方針は運用担当）。
- 文書同期（第9章）。テスト件数は実測できたときだけ追記。未測なら「未測」と書く。
- 旧再開ZIPを復元しない。hash 付き manifest と旧ZIPとの差分。

完了条件: 文書の矛盾が説明付きで解消。コード無しでも可。

### 単位1 — P0-1 正確性（順序2の前半）

範囲: `MoneyParseResult` / `parse_money`、add/finish/CSV、REVISION 更新、Excel例外表示。

完了条件: 要確認が無警告0円で確定しない。数値0が actual。第1章の試験1–7。既存仮定ゼロ試験を真正欠損に限定して維持。全体車両試験が緑。この時点では独立原本照合未完成なので、確定用途へ配備しない。

並行可: P1-1 の API スキーマ文書化（実装は単位3）。

### 単位2 — P0-2 + P0-3（順序2の後半）

分割が必要な場合:

- **2A:** データモデルと `reconcile_sources` 純粋関数（空配列合格をテスト上で禁止できるところまで）。
- **2B:** Excel/CSV/PDF adapter への control・invoice 抽出、鑑の control 化、請求指紋、部分抽出。
- **2C:** workflow/goal gate/Excel 原本照合シートへの接続。

同一PRにすると差分が大きいので連続PRでも可。ただし 2A だけで鑑除外のままゲートを「完成」扱いにしない。

完了条件: 欠落・重複・空controls・別請求共存・部分差分・control unavailable の試験。既存 `test_csv_pdf_duplicate_is_not_double_counted` を新仕様へ更新。確定完了が独立合計なしで True にならない。P0 focused test と全体回帰。実原本のコピー確認は本番データ変更とは別承認。

単位1の後。

### 単位3 — P1-1 第一段階UI（順序2並行〜順序3の入口）

範囲: workflow-readiness、先頭の停止理由、ボタン可否、同一案件のポーリング、暫定/確定ラベル（判定は単位2の関数を呼ぶ）。永続ジョブ表は含めない。

完了条件: 第4章のAPI試験。未実装機能が allowed に出ない。P0不一致が実行可能表示にならない。

単位2の確定定義に依存。表示骨格だけ先に出すなら complete をまだ出さない。

### 単位4 — P1-2 接続（順序3）

範囲: 対応表の開発分離維持、公開文再セット、永続ジョブ/idempotency、再開位置、lifecycle、外部送信の明示承認。車両専用指摘を文章で閉じない試験。

完了条件: 画面操作に相当するAPI列が途中失敗を保持したまま再検証まで進める。ゲート迂回なし。予算待ち、外部送信後クラッシュ、development blocker、版競合。

### 単位5 — P1-3 配賦（順序3）

範囲: assignments、decide の月粒度、継承、保険列の拒否リスト、仮定ゼロ整理、UIの月別配賦表。業務仕様未確定部分は確定不可状態に留める。

完了条件: 乗替・複数配賦・原本変更・未確定・社会保険明示額・本人控除拒否の試験。

単位1必須。実原本49件の通常経路受入はこの単位の後（抽出が正確で、配賦が月別）。

### 単位6 — 実原本受入（順序3の実証、別セッション）

範囲: 最新計画を P0/P1 の契約へ更新。登録原本から通常経路で準備→検証→承認→実行→暫定/確定判定。独立照合記録とExcel。

### 単位7 — P2-1（順序4）

範囲: RecipeSpec 版管理、adapter/mapping/applicability/validation、fresh source extraction への実接続。allocation_rules を含めるなら単位5後。

完了条件: 別月・別 source hash で再利用。条件不一致拒否。金額非再利用。独立原本照合合格。

単位7の後が安全。人間承認済みの確定成果が前提なので単位6の後が望ましい。

### 単位9 — 検証記録（順序5）

範囲: 関連 focused test、全体 test、可能なら `scripts/healthcheck.ps1`。BUILD_REPORT 最新サマリー。未達条件、対象版、環境、件数、log。新しい再開 manifest。旧ZIPは履歴保持。Docker は Web UI のデプロイ機能。本エージェントは docker 不可。

## 12. テスト戦略

- poll、非表示停止、通信失敗。

## 13. 業務仕様として確認が必要な事項

**採用: ChatGPT版の29項目（5分野）を土台に、GROK版にあって重複しない現行コードの具体的矛盾を追加。推測で埋めない。実装前、遅くとも該当実装単位の開始前に業務責任者へ確認する。**

番号は統合後の通し番号。括弧内は由来。

### 13.1 会計・金額

1. **売上の税区分の統一。**（ChatGPT 1 + GROK 5）税込・税抜のどちらへ統一するか。混在時の消費税処理と確定可否。**現行コードの矛盾:** 台帳月別売上は `exclusive`、汎用台帳は費目依存（給与・保険は `non_taxable`、それ以外は `inclusive`）。混在すると利益を出さない（現行）。台帳が税込なら exclusive は誤り。原本の列定義を確認する。
2. **燃料費の採用列と内外税。**（ChatGPT 2 + GROK 3）「金額」「参考消費税」「軽油税」「合計金額」のどれを採用し、vendor 別にどの列が内税/外税か。**現行:** CSVで「合計金額」が無いとき参考消費税+軽油税を加算する。独立合計が税込総額か、商品代+税か。鑑と明細で税の扱いが違う可能性。
3. **値引、返品、相殺、マイナス請求の扱い。**（ChatGPT 3）
4. **請求月と利用月/給油月が異なる場合、どちらの月へ計上するか。**（ChatGPT 4）
5. **リース開始・終了月。**（ChatGPT 5 + GROK 4）日割り有無。現コードは月内なら全額計上（開始・終了月 inclusive）。途中解約・非課税の扱い。
6. **円未満端数と複数車両配賦時の丸め差をどの車両へ付けるか。**（ChatGPT 6）現行丸めは `yen_half_up`。
7. **「その他費用」に含める費目と対象外費目。**（ChatGPT 7）
8. **根拠付き除外を承認できる役割と、必要な証拠。**（ChatGPT 8）
9. **不足0円方針の対象費目。**（GROK 1、ChatGPTに無し）全 CATEGORIES か、高速・その他など一部か。現行は全費目に仮定ゼロを撒く。
10. **実額ゼロの配賦確認。**（GROK 2、ChatGPT 10とは別）金額0で車両候補が複数のとき、確認するか無視するか。現行 `if not allocations and amount:` は0円を確認に回さない。

### 13.2 車両・配賦

11. **社員の月中乗替の配賦基準。**（ChatGPT 9 + GROK 6）日単位、勤務日数、走行距離、売上、均等のどれか。**現行コード:** 台帳列「開始/終了」はリース用。乗替日が給与側・別表・口頭のどれか。無い場合は常に確認か。未決の間は確認へ回し、一括配賦しない。

13. **代車、休車、廃車、新規登録、旧車番併記の同一車両判定。**（ChatGPT 11）
14. **車両台帳上の会社と請求会社が異なる場合の処理。**（ChatGPT 12）

21. **社員が複数会社・複数車両へ関与する場合の配賦基準。**（ChatGPT 18）

### 13.5 承認・外部検証・再利用

28. **外部AI検証で全 provider pass を必須とする現行規則を維持するか。**（ChatGPT 24）
