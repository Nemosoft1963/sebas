## やること(設計書 第5章 5.1〜5.3節どおり)

### 1. 対応表の拡張(5.1節)
既存キーを維持しつつ、`targets`(type/id)と`binds`(goal_criterion_ids/task_key/contract_patch/test_ref)を追加。
- `disposition`の意味を明確化: `amend`(説明追記+契約を変えない確認手順の具体化。専用器の動作は変えない)、
  `rebuild_vehicle`(現行どおり、抽出工程欠落の旧計画のみ。現行4工程への再構成は禁止)、
  `development`(P0/P1-3/P2のコード欠落。apply不可・start不可)、`business_fact`(P1-3の所属・乗替等)、
  `unresolved`(根拠不足)。
- **`contract_fix`(任意の契約パッチ)は初期実装に入れない。** `targets`はスキーマ予約に留める。
  不合格patchを保存・適用しない。

### 2. 指摘ライフサイクル(5.2節)
`imported -> classified -> proposed -> applied -> revalidation_pending -> validated | rejected | development_pending | business_fact_pending`
「文章に追加しただけ」でvalidatedにしない。解決条件は新plan_signatureへの外部検証結果、対応したテスト/契約、
または明示された業務事実回答。

### 3. オーケストレーションとジョブ(5.3節)
1. feedback import → 2. local proposal → 3. human confirmation → 4. apply →
5. public packet regeneration(`public_draft()`で再生成、自動送信はしない) →
6. explicit send approval → 7. external re-review/budget queue → 8. plan human approval → 9. execution start
- 外部送信はstep6なしに自動遷移しない。
- plan/source/requirements hashが変わればstep5へ戻す。
- ReviewStoreの`kind='job'`または共通ジョブ表を導入。`propose`/`review_plan`/`prepare`開始時にidを返し、
  単位3のreadinessが拾う。同一idempotency_keyのrunning/succeededがあれば二重実行しない。
- 外部送信済みか不明なクラッシュは自動再送せず`needs_attention`。
- 再読込でgenerating/runningを復元。二重は409。
- `last_completed_stage`と`blocking_error`を保存。

## テスト
設計書 第5章「受入条件の検証方法」1〜7を実装:
1. 通常経路結合試験(import→propose(amendのみ)→apply→新署名でrequire_review失敗→review_plan mock pass→
   startがゲートを越える。擬似中断後の再開位置確認)
2. developmentが残る指摘: apply 409、start 409。車両専用指摘をamendで閉じられないこと
3. 計画版変更後、旧署名のreview passedをrequire_reviewが拒否
4. 外部送信: safe_to_send=Falseで失敗。packetに原本本文が無い(既存試験維持)
5. 外部送信直後のクラッシュはneeds_attention
6. 外部AI未許可・provider未設定時は送信ボタン無効化、ローカル修正は利用可能
7. 再読込後にactive_jobとresume_fromが復元
