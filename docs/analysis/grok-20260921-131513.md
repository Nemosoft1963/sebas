# 1. 概要(目的・主な機能・技術スタック)

**目的:** Windows 11 + Docker Desktop + ホスト側 Ollama 上の、ローカル優先の AI 共同作業環境。チャットだけでなく、プロジェクト単位で目標→計画承認→依存付き実行→成果物・監査記録までつなぐ。外部 AI は明示許可時のみ助言者として使う。根拠: `README.md` 冒頭、`SYSTEM_DESCRIPTION_FOR_AI.md` 1章、`AGENTS.md`。

**主な機能(コードで確認できたもの):**
- 統合フロント(FastAPI)によるプロジェクト・会話・計画実行・Workspace・コンテキスト原本。入口は `app/web.py` の `app = FastAPI(...)` (329行付近) と lifespan (247行〜)。
- 目標からの計画生成・承認・並列実行。`app/project_manager.py` の `ProjectOrchestrator`。
- 宣言型の安全な表処理、弥生 Excel 確認、公開 Web 収集、承認付き外部アクション、プレマーケティング(Google Forms/Sites、SNS 文案、Canva)。API 群は `app/web.py`。

- TRIZ 収集 JSON の変換・HTTP 投入 CLI(既存 API を変更せず追加)。`app/triz_import.py`、`scripts/import_triz_problems.py`。
- 経験 RAG(opt-in、既定 off)。`app/experience_memory.py`、`EXPERIENCE_RAG_OPERATIONS.md`。
- 音声: Web 経路は faster-whisper、コンソール経路は Qwen ASR/TTS。`app/web.py` の `/api/transcribe`、`app/main.py`。

**技術スタック:**
- Python 3.11–3.13 / FastAPI / Uvicorn / httpx / SQLite。`pyproject.toml`、`docker/Dockerfile`(Python 3.12-slim)。
- Docker Compose: `web`(8099)、`open-webui`(3000)、`cptr`(8000)、`google-publisher-browser`(8010)、profile `phase2` の Qdrant。`docker-compose.yml`。
- ローカル LLM: ホスト Ollama (`host.docker.internal:11434`)。
- フロント UI: `app/static/*.html|js|css`。

# 3. 起動方法と実行の流れ(入口 → 主要処理)

**推奨起動(文書・スクリプト):**
1. `scripts/preflight.ps1` → `setup.ps1` → `pull-models.ps1` → `start.ps1`。根拠: `README.md`、`SYSTEM_START_STOP.md`。
2. `scripts/start.ps1` は `.env` が無いか `WEBUI_SECRET_KEY` が空なら `setup.ps1` を呼び、`docker compose up -d`、マイクブリッジ、`http://127.0.0.1:8099/api/health` 待ち、`POST /api/control/start`。根拠: `scripts/start.ps1` 1–48行。
3. コンテナ内 CMD: `uvicorn app.web:app --host 0.0.0.0 --port 8000`。ホスト公開は `127.0.0.1:8099:8000`。根拠: `docker/Dockerfile` 最終行、`docker-compose.yml` ports。

**Web 起動時の流れ(`app/web.py` lifespan 247–326行):**
1. `ShortTermMemory(DB_PATH)` を開き、running ミッションを paused へ復元(`short_term.py` コンストラクタ後半)。
2. `Ollama`、`WorkspaceSandbox`、`ProjectOrchestrator` を生成。
3. 目標レビューキュー、Google 同期ループ、モデルウォームアップを起動。
4. completed なのに未完了タスクがあれば paused へ戻す。
5. agent-examples / procedure-learning の install が lifespan をラップし、中断ジョブを failed にする。根拠: `app/agent_examples_api.py` recover、`app/procedure_learning_api.py` 末尾 lifespan。

**通常チャット:** ブラウザ → `WS /ws/chat` → プロジェクトコンテキスト + 履歴 → ローカル LLM(または `FRONT_AI_PROVIDER`) → SQLite `turns`。根拠: `app/web.py` `chat`。

**計画実行:** 目標保存 → 計画生成 → 承認 → start → `_run` が依存を満たすタスクを並列実行 → Workspace/table 操作を検証して完了。根拠: `README.md`、`app/project_manager.py`。

**TRIZ 分野横断:** 実行例 POST → learning GET/POST `/general` → ケース登録 → generate → experiment → review。根拠: `app/triz_general_api.py`、`app/procedure_learning_api.py` の `install_general_triz`。

**別入口:** `python -m app.main`(`app/main.py`)。Docker web とは独立。

# 8. 改修する際の注意点(壊れやすい箇所、依存関係、触る順序の提案)

**壊れやすい箇所**
- `procedure_learning_api.install` が TRIZ 両系統を同じ router・同じ `busy()` ロックに載せる。学習ジョブ中は `/general` POST が 409。取込 CLI はこれを再試行する。根拠: `app/triz_general_api.py` `busy`、`scripts/import_triz_problems.py` `MAX_RETRIES`。
- `ExampleStore.change` / `LearningStore.change` は revision 楽観ロック。UI と CLI の同時操作で 409。
- `general_inventions` は learning JSON 内。スキーマ変更は既存行の互換が必要。
- Workspace は resolved path + parent 判定。prefix 比較に戻さないこと。`app/workspace_files.py` `_inside`。
- 計画の `acceptance_criteria` JSON 契約。`app/structured_planning.py` と連携。未読だが `project_manager.py` から多用。
- lifespan の多重ラップ。agent-examples と procedure-learning が順に `app.router.lifespan_context` を差し替える。順番依存。

**依存関係**
- 分野横断 TRIZ は「プロジェクト」→「実行例」→「learning state」の順。実行例なしでは `/general` が 404。
- 取込 CLI は稼働中 HTTP API を叩く。pytest の TestClient 経路とは別。
- アダプター実行はローカル Ollama の JSON schema。ダミー LLM なしでは generate/experiment は動かない。

**触る順序の提案**
1. 安全既定(`FRONT_AI_PROVIDER`)と文書のテスト件数を事実に合わせる(既存挙動の確認を先に)。
2. TRIZ 取込は既存 API を変えず、変換・CLI・テストの追加で足りる状態が既にある。本体改修が必要なら `triz_common.validate_problem` の None 処理を、既存テスト(`test_triz_general` 等)と一緒に直す。
3. `web.py` 分割は API 契約と lifespan install 順をテストで固定してから。
4. 計画実行・車両・プレマーケティングはそれぞれ専用テストがあるので、横断リファクタは後回し。
5. 実 8099 投入は人間承認・対象プロジェクト確定後。dry-run を先に。
