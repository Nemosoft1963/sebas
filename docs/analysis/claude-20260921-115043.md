# 1. 概要(目的・主な機能・技術スタック)

## 目的（事実）
- Windows 11 + Docker Desktop + Ollama を前提とした「ローカル優先のAI共同作業環境」。ローカルLLMが統制・最終判断を行い、外部AI（Claude/ChatGPT/Gemini/Grok/Meta）は明示許可時のみ利用する。根拠: `README.md` 冒頭、`SYSTEM_DESCRIPTION_FOR_AI.md` §1・§1.1。
- 設計思想として「外部AIを最終決定者にしない」「Workspaceを限定」「未検証を成功と報告しない」が全体に貫かれている。根拠: `SYSTEM_DESCRIPTION_FOR_AI.md` §1、`AGENTS.md`、各モジュールのdocstring（例 `app/triz_adapters.py` 冒頭 "Explicit local adapters: artifact trials, never arbitrary host execution."）。

## 主な機能（事実）
| 機能群 | 実体 |
|---|---|
| ローカルチャット（WebSocket） | `app/web.py` の `@app.websocket("/ws/chat")` |
| プロジェクト/固定コンテキスト/資料登録 | `app/web.py` `/api/projects*`, `app/memory/short_term.py` |
| 目標→計画生成→承認→依存関係付き並列実行 | `app/web.py` `/api/projects/{id}/mission/*`、`app/project_manager.py`（未読）|

# 3. 起動方法と実行の流れ(入口 → 主要処理)

## 起動（事実）
- Docker: `docker-compose.yml` の `web` サービス → `docker/Dockerfile` の `CMD ["uvicorn","app.web:app","--host","0.0.0.0","--port","8000"]`。ホストへは `127.0.0.1:8099:8000` で公開。
- 運用は PowerShell スクリプト（`scripts/start.ps1` / `status.ps1` / `healthcheck.ps1` / `stop.ps1`）。根拠: `README.md`「通常運用」、`scripts/` 一覧。
- 非Web（音声CLI）: `app/main.py` の `main()`（`scripts/start-console.ps1 -Voice`）。`config/settings.yaml` を読み、`data/memory/conversations.db` を使う。**Web版とDBパス/設定読み込み系統が異なる。**

## 起動時シーケンス（`app/web.py` `lifespan`）
1. `ShortTermMemory(DB_PATH)` 生成（＝この時点でスキーマ作成・マイグレーション・running→paused復旧が走る。`app/memory/short_term.py` `__init__`）
2. `Ollama(OLLAMA_URL, OLLAMA_MODEL)`、`WorkspaceSandbox(WORKSPACE_ROOT)`、`ProjectOrchestrator(...)` 生成
3. `goal_review_queue.loop` を `asyncio.create_task`
4. `GoogleFormsPublisher(GooglePremarketingConfig.from_env())`、`_google_sync_loop()` 起動
5. `engine_enabled` なら `_warmup_selected_model()`
6. 全プロジェクトを走査し、`completed` なのに未完了タスクが残るものを `paused` に戻す＋`write_project_memos`
7. さらに `agent_examples_api.install` と `procedure_learning_api.install` が **lifespan_context を二重にラップ**しており、それぞれの復旧処理（中断ジョブの `failed` 化）が追加される。

## 主要フロー
- **チャット**: ブラウザ → `/ws/chat` → `shared_project_context()`（固定コンテキスト＋資料本文＋会話履歴）→ 外部フロントAI（設定時）→ 失敗時 `llm.stream()` → `memory.save()`。
- **計画実行**: `PUT /mission` → `POST /mission/plan/generate`（`orchestrator.generate_plan`）→ `/plan/approve` → `/mission/start` → `/pause` `/retry` `/verify`。
- **TRIZ（分野横断）**: `POST /api/projects/{pid}/agent-examples`（記録取込→`eid`）→ `POST .../learning/general`（課題定義）→ `POST .../learning/general/{sid}/cases`（原本＋期待結果）→ `POST .../general/{sid}/generate`（202, 非同期）→ `POST .../general/{sid}/experiment`（202）→ `POST .../general/{sid}/review`。根拠: `app/triz_general_api.py`, `app/procedure_learning_api.py`。

# 7. リスクと技術的負債

| # | 重大度 | 内容 | 根拠 |
|---|---|---|---|
| R1 | **高** | **`validate_problem` が `None` を文字列 "None" にしてしまう。** `problem={k:str(values.get(k,'')).strip() ...}` のため、`physical: null` が `"None"` として保存され、そのままLLMプロンプト（`reasoning_context`）に入る。`inputs/triz-problems-export.json` の大半が `"physical":null` なので取り込み時に確実に踏む。 | `app/triz_common.py` `validate_problem` / 入力JSON |

# 8. 改修する際の注意点

## 壊れやすい箇所
1. **`app/web.py` の `lifespan` とグローバル変数**：ここを触ると全機能に波及。`install()` によるルーター後付け（`_sys.modules[__name__]` を `env` として渡す）は循環参照に近い構造で、`env.memory` / `env.DATA_DIR` / `env.llm` / `env.require_project` / `env.DB_PATH` に依存している。属性名を変えると TRIZ/学習系が一斉に壊れる。
2. **`LearningStore` の JSON スキーマ**：`item` に `cases/recipes/runs/jobs/corrections/capabilities/semantics/inventions/general_inventions` があることを多数の関数が暗黙に前提とする（`LearningStore.get` の初期値には `inventions`/`general_inventions` が**含まれない**ため、`setdefault` 依存。`app/triz_invention.new_session` と `app/triz_general.create` が `setdefault` で作る）。キー追加は後方互換に注意。
3. **`signature()` / `cases_hash()` による凍結**：`app/triz_general.signature` は `{adapter_version, domain, problem, criteria, cases}` のfingerprint。ここに1フィールド足すと**既存の採用済み候補が全て失効**する（`eligibility` が `signature` 一致を要求）。`ADAPTER_VERSION` も同様。
4. **`readiness`/`adopt`/`can_adopt` の相互依存**：`app/procedure_learning.readiness` → `app/triz_invention.can_adopt` → `session()` という循環に近い依存があり、片方の状態名（`operational`/`superseded`/`revoked`/`needs_revalidation`）を変えると採用判定が崩れる。
5. **DBマイグレーション**：`short_term.py` は `PRAGMA table_info` で列の存在を見て `ALTER TABLE ADD COLUMN` する追加型。**列削除・型変更の仕組みは無い**。追加型を守ること（`SYSTEM_DESCRIPTION_FOR_AI.md` §16.2 と一致）。
6. **`replace_plan` の完了状態引き継ぎ判定**：`acceptance_criteria` をJSONとしてパースし `criterion`/`action_requirements`/`outputs`/`public_web_research` を比較して `preserve` を決める。契約スキーマを変えると過去の完了タスクが一斉に `pending` に戻る。

# 9. TRIZ収集データの取り込み案

## 9.1 既存の入力口（事実）

**結論：既存の受け口は「分野横断TRIZの課題定義API」＝ `POST /api/projects/{pid}/agent-examples/{eid}/learning/general` である。**

- ルーター定義: `app/procedure_learning_api.py` `router=APIRouter(prefix='/api/projects/{pid}/agent-examples/{eid}/learning')`、末尾で `install_general_triz(router, LearningChange, store, state, safe, edit, schedule, model_json, folder)`。
- エンドポイント: `app/triz_general_api.py`
  ```python
  @router.post('/general')
  async def new(pid, eid, body: Change):
      def update(item): busy(item); create(item, body.values)
      return edit(pid, eid, body, 'general_triz_created', update)
  ```
- リクエストボディ: `LearningChange{revision:int, values:dict}`（`app/procedure_learning_api.py`）。
- `values` の必須項目（`app/triz_general.create`）:
  - `domain` ∈ `app/triz_adapters.DOMAINS` = `documents, research, software, workflow, operations, browser, general`
  - `validate_problem(values)` が要求する8フィールド = **エクスポートJSONのキーと完全一致**（`goal, improve, worsens, ideal, physical, constraints, resources, evidence`）。`physical` のみ空可、他は非空かつ各2500文字以内。
  - `human_checks`（1〜3000文字、必須）
  - `max_seconds`（1〜900、既定300）
  - `metrics`（6件以内、任意）

### 入力JSONとの適合（実データで確認）
| export のキー | `triz_common.FIELDS` | 適合 |
|---|---|---|
| goal / improve / worsens / ideal / physical / constraints / resources / evidence | 同名 | **8/8 一致** |
| domain | `DOMAINS` のキー | 確認した全item が `"software"` → 有効値 |
| （無し） | `human_checks` | **不足 → 補う必要あり** |
| （無し） | `max_seconds`, `metrics` | 既定値でよい |

## 9.2 必要な変換（具体）

1. **前提となる `eid` の確保**：`/general` は `state(pid,eid)` → `source(pid,eid)` → `ExampleStore.get(pid,eid)` を経るため、**先に `POST /api/projects/{pid}/agent-examples`（`ImportBody{filename, source, agent}`）で1件の「実行例」を作る必要がある**。`ExampleStore.import_text` は `.md/.txt/.json` を許容し、`.json` は `json.loads` で検証するので、`inputs/triz-problems-export.json` 自体を `source` として投入できる（5MiB上限・NUL禁止）。→ 取り込み元の原本性（SHA-256は `ExampleStore` が算出）も残せる。
2. **`physical: null` の処理（R1対策）**：`validate_problem` が `str(None)` → `"None"` にするため、**変換側で `physical` が `None` なら空文字 `""` に落とす**こと。`"False"`（文字列）が入っている item もあるので（例: `"physical":"False"`）、そのまま渡すと「相反する性質＝False」という無意味な記述になる。空文字化かスキップの方針決定が必要。
3. **`human_checks` の生成**：機械生成の定型文（例「出典URLの引用が原本と完全一致し、未実施の効果を成功と述べていないことを人が確認する」）を与えるか、UI側で必須入力にする。**自動生成した定型文を「人の確認済み」と誤解させない**記述にすること（`app/triz_general.review` は別途 `reviewer`/`evidence` を要求するので、安全境界自体は維持される）。
4. **文字数上限**：各フィールド2500文字。`evidence` は「出典URL＋取得日時＋SHA-256＋ライセンス＋根拠引用」の複数行で、実データ上は最長でも数百文字なので問題ない見込み（実測はしていない＝推測）。
5. **`revision` の取得**：`LearningChange.revision` は現在値と一致必須（`LearningStore.change` が `Conflict`）。1件投入ごとに `GET .../learning` で `revision` を取り直すか、`store().update()` 相当のリトライを行う。UIの `triz_general.js` も毎回 `state()['revision']` を読んでいる（`post()` 関数）。
6. **`busy()` ガード**：`app/triz_general_api.new` は `busy(item)` を呼び、`jobs`/`runs` に pending/running があると 409。一括投入時はジョブ完了を待つ。

## 9.3 実行・検証まで進める場合に不足するもの（重要）

- **比較試験（`/general/{sid}/experiment`）には `cases` が必須**。`add_case` は `resources`（1〜6件、各 空でない24000文字以内の**本文テキスト**）と `expectations.evidence`（独立した合格基準の根拠）を要求する。**エクスポートJSONには原本本文が無い**（あるのは出典URLと短い引用のみ）。したがって取り込みだけでは試験は実行できず、`status='defined'` → `generate` で候補生成までが上限。
- **`domain='software'` の追加要件**：`create` が `runtime_test_required=True` を立て、`review(decision='adopted')` は `runtime_tests_passed` と `runtime_evidence` を必須にする（`app/triz_general.review`）。また `TERMINAL['software']='code.patch'` で最終工程が `code.patch` 固定、`execute_step` は `code.patch` の原本を `.py` 限定にする（`app/triz_adapters.execute_step`）。→ **software ドメインで試験するには Python 原本の登録が前提**。
- 代替として `domain='general'` を選ぶと `TRIZ_CAPABILITIES['general.action'].available=False` のため、候補は `plan_only`（実験計画のみ保存）になる。`tests/test_triz_general.py::test_browser_plan_survives_without_connector` が同じ挙動を確認済み。

## 9.4 推奨する取り込み方式（案）

> 方針: **新規CLIスクリプト（例 `scripts/import_triz_problems.py`）を追加し、既存HTTP APIを叩く**。アプリ本体（`web.py`）には手を入れない。理由: `/general` は既に完全な入力口であり、DB直書きは `revision`・`busy`・監査履歴（`history` テーブル）を迂回してしまうため。

処理手順:
1. `inputs/triz-problems-export.meta.json` の `sha256` と実ファイルのSHA-256を照合（改ざん検出）。不一致なら停止。
2. `POST /api/projects/{pid}/agent-examples` に export JSON 全体を投入 → `eid` 取得（既存なら同一hashで既存itemが返る＝冪等）。
3. items を1件ずつループ:
   - `GET .../learning` で `revision` 取得
   - `values = {**item, physical: item.physical or "", domain: item.domain, human_checks: <定型>, max_seconds: 300}`
   - `POST .../learning/general`
   - 409（`busy`/`Conflict`）時は待機・再取得して再試行、422 は内容を記録してスキップ
4. 結果（成功/スキップ/理由）をレポート出力。
