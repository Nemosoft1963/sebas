# 1. 概要(目的・主な機能・技術スタック)

## 1.1 目的
「Local Cowork + Local Voice AI」は、Windows 11、Docker Desktop、Ollamaを基盤とするローカル優先のAI共同作業環境です（`README.md` 3行目、`SYSTEM_DESCRIPTION_FOR_AI.md` 23-35行目）。機密情報・社内資料・財務データを外部に無断送信せず、ローカルLLMを統制者・最終決定者としてタスク計画の生成・検証・並列実行、音声入出力、表データ処理、および事例ベースの手順学習（TRIZ等）を行うことを目的としています。

## 1.2 主な機能
1. **ローカル優先チャット・統制**: WebSocket `/ws/chat` を通じたストリーミング応答。プロジェクトごとの固定コンテキストおよび登録資料をローカルLLMに渡して回答（`app/web.py` 1083-1144行目）。
2. **目標からの作業計画生成・承認・依存関係付き並列実行**: プロジェクト目標からタスク依存関係を持つ計画をローカルLLMが立案し、人間の承認後に独立タスクを並列実行（`app/project_manager.py`、`app/web.py` 246-302行目）。
3. **明示許可制の外部AI調査・レビュー**: Claude、ChatGPT、Gemini、Grok、Meta Llama等の外部AIは、ユーザーが明示的に許可・選択した場合にのみ調査や計画評価に利用し、結果の統合・採否判定はローカルLLMが行う（`app/external_ai.py`、`SYSTEM_DESCRIPTION_FOR_AI.md` 153-167行目）。
4. **安全な専用Workspace操作**: `/workspace` 配下に限定し、`mkdir`、`write_text`、`append_text`、`copy`、`move` のみ許可。削除・任意シェル実行・シンボリックリンク脱出を遮断（`app/workspace_files.py`、`AGENTS.md` 5-34行目）。
5. **安全な表データ実行器 (SafeTableExecutor)**: CSV/TSV/XLSX/XLSMを宣言的JSON定義に従って集計・結合・加工（`app/tabular_data.py`）。
6. **音声入出力**: ブラウザ録音 + Docker内 `faster-whisper`（smallモデル、CPU/int8）による文字起こし、およびWindowsホスト側マイクブリッジ（`app/web.py` 1007-1051行目、`app/mic_bridge.py`）。
7. **弥生会計Excel確認支援**: 仕訳・試算表の構造解析とプレビュー（`app/yayoi_accounting.py`）。
8. **プレマーケティング / Google連携 / Canva連携**: Googleフォーム作成・回答同期、LP資材生成、Canva連携（`app/google_premarketing.py`、`app/landing_page.py`、`app/canva_connect.py`）。
9. **手順学習・TRIZ発明支援**: 過去の作業記録や承認済みTRIZ課題からの矛盾解消・手順抽出・実験・再利用（`app/procedure_learning.py`、`app/triz_general.py`、`app/triz_invention.py`）。
10. **経験RAG・外部AI回答キャッシュ**: 過去の成功/失敗教訓の蓄積と完全一致回答キャッシュ（`app/experience_memory.py`、`EXPERIENCE_RAG_DESIGN.md`）。

## 1.3 技術スタック
- **バックエンド**: Python (>=3.11, <3.14), FastAPI (>=0.116, <1), Uvicorn, SQLite3, HTTPX, Pydantic, PyYAML, openpyxl, pypdf, faster-whisper (`pyproject.toml` 6-17行目)
- **フロントエンド**: HTML5, Vanilla JavaScript, CSS3（`app/static/` 配下）
- **コンテナ / インフラ**: Docker, Docker Compose (services: `web`, `open-webui`, `cptr`, `google-publisher-browser`, optional `qdrant`) (`docker-compose.yml`)
- **LLM / 推論環境**: Ollama (Windowsホスト `127.0.0.1:11434`), 既定モデル `gpt-oss:20b` (`.env.example` 2行目)
- **テスト基盤**: pytest, pytest-asyncio (`pyproject.toml` 15行目)

# 3. 起動方法と実行の流れ(入口 → 主要処理)

## 3.1 起動方法
1. **Docker Compose による全体起動** (`README.md` 43-55行目、`docker-compose.yml`):
   ```powershell
   .\scripts\start.ps1
   ```
   - `web`: FastAPI サーバー（`127.0.0.1:8099:8000`）
   - `open-webui`: チャット / Knowledge（`127.0.0.1:3000:8080`）
   - `cptr`: Open WebUI Computer（`127.0.0.1:8000:8000`）
   - `google-publisher-browser`: 専用ブラウザ（`127.0.0.1:8010:8000`）
2. **スタンドアロン音声コンソール** (`app/main.py` 32-40行目):
   ```powershell
   .\scripts\start-console.ps1 -Voice
   # または
   python -m app.main --voice
   ```

## 3.2 実行の流れ

### A. 通常チャット (`/ws/chat`)
1. **接続**: クライアントが `/ws/chat` にWebSocket接続。`session_id` を発行または受領（`app/web.py` 1083-1087行目）。
2. **コンテキスト構築**: `project_id` と `session_id` から `shared_project_context` を呼び出し、登録資料目録・本文抽出テキスト・過去の会話履歴を結合（`app/web.py` 210-227行目、1096行目）。
3. **推論実行**: `FRONT_AI_PROVIDER`（既定 `ollama`）により、Ollama (`http://host.docker.internal:11434`) へストリーミングリクエスト（`app/web.py` 1109-1133行目）。
4. **永続化**: 生成トークンをクライアントへ逐次送信し、完了後にターン情報（質問、回答、モデル名、処理時間）をSQLite `turns` テーブルへ保存（`app/web.py` 1137行目）。

### B. プロジェクト目標・計画実行フロー
1. **目標設定**: 利用者が目標・達成条件・制約を入力し、`PUT /api/projects/{project_id}/mission` を呼び出し（`app/web.py` 267-285行目）。
2. **計画生成**: `POST /api/projects/{project_id}/mission/plan/generate`
   - ローカルLLMがタスク草案をJSON Schemaで生成（`app/project_manager.py`、`app/web.py` 299-317行目）。
   - 外部AI利用が明示許可されている場合は、外部AIによるレビューを経てローカルLLMが高度化。
3. **計画承認**: 人間が内容を確認し、`POST /api/projects/{project_id}/mission/plan/approve` で承認（`app/web.py` 320-326行目）。
4. **依存関係付き並列実行**: `POST /api/projects/{project_id}/mission/start`
   - `ProjectOrchestrator` が依存関係（`depends_on`）が満たされたタスクを `max_parallel_tasks`（1〜4）の範囲で並列実行（`app/project_manager.py`、`app/web.py` 329-336行目）。
   - タスク内のファイル操作は `WorkspaceSandbox` 経由で allowlist 操作（`mkdir`, `write_text` 等）のみを反映（`app/workspace_files.py`）。
   - 必要に応じて `SafeTableExecutor` による宣言的表データ処理を実行（`app/tabular_data.py`）。
5. **備忘録自動生成・完了報告**: タスク進捗や成果に応じて `__project_memory__/` 配下にMarkdown備忘録が生成され、最終報告書としてダウンロード可能になる（`app/project_memos.py`、`app/web.py` 1060-1077行目）。

2. **多重同時アクセス・高負荷耐性テスト**: 単一ユーザーを想定した設計のため、高並行アクセス時のSQLiteロック競合やメモリ枯渇に関するストレステストが不足しています。

# 7. リスクと技術的負債(ファイルパスと根拠付き。重大度: 高/中/低)

## 7.1 重大度: 高
1. **認可・認証基盤の欠如（localhost境界依存）**
   - **根拠**: `app/web.py` 全体でユーザー認証やRBAC、CSRFトークン検証が実装されておらず、すべてのAPIが非認証でアクセス可能（`SYSTEM_DESCRIPTION_FOR_AI.md` 384-391行目）。
   - **リスク**: `0.0.0.0` へのバインドやリバースプロキシの誤設定により、ネットワーク上の第三者が機密データ閲覧や任意Workspaceファイル書き込みを行える。
2. **単一巨大ファイル (`app/web.py`) への責務集中**
   - **根拠**: `app/web.py` が1,500行を超え、Webルーティング、プロセス管理、ライフサイクル、メール送信、外部連携、チャット制御が混在。
   - **リスク**: 修正時の意図しない副作用やリグレッションの発生リスクが極めて高い。

## 7.2 重大度: 中
1. **SQLite への高頻度同時アクセスによるロック競合 (`database is locked`)**
   - **根拠**: `app/memory/short_term.py`、`app/procedure_learning.py`、`app/triz_general.py` 等が個別にSQLiteトランザクションを発行。
   - **リスク**: 並列タスク数やジョブが増加した際に `sqlite3.OperationalError: database is locked` や 409 Conflict が多発する可能性。
2. **外部AIのモデル名変更・破壊的API改変への脆弱性**
   - **根拠**: `app/external_ai.py` 53-83行目にモデル名がハードコードまたは環境変数指定されており、外部プロバイダの廃止・変更時にサイレントエラーまたはパース失敗になる。

## 7.3 重大度: 低
1. **インメモリ状態（`executions`）の再起動時消失**
   - **根拠**: `app/web.py` 69行目の `executions: dict[str, dict] = {}`。
   - **リスク**: サーバー再起動時に直近の実行進捗モニター情報がリセットされる（永続イベントはDBに残るためデータ損失ではない）。

3. **データ移行・DBスキーマ変更 (`app/memory/short_term.py`)**
   - 既存のDB列・行を破壊しない「追加型マイグレーション」を厳守する。`DROP TABLE` や破壊的変更は禁止。

# 9. TRIZ収集データの取り込み案(既存の入力口、必要な変換、検証方法)

## 9.1 既存の入力口
本システムには、承認済みTRIZ課題を取り込むためのAPIおよびスクリプトが**すでに実装されています**。
- **入力口 API**: `POST /api/projects/{pid}/agent-examples/{eid}/learning/general` (`app/triz_general_api.py` 33-36行目)
- **インポートスクリプト**: `scripts/import_triz_problems.py` (`scripts/import_triz_problems.py` 1-182行目)
- **変換モジュール**: `app/triz_import.py` (`app/triz_import.py` 1-84行目)

## 9.2 入力データの形式 (`inputs/triz-problems-export.json`)
- メタ情報: `inputs/triz-problems-export.meta.json` に SHA-256 (`8d9462...`)、件数 74件、フォーマット `localsaporter-problem-definition` が記録されている。
- データ構造:
  ```json
  {
    "export": {
      "exported_at": "2026-09-21T12:02:57Z",
      "format": "localsaporter-problem-definition",
      "format_version": "1",
      "items": [
        {
          "domain": "software",
          "goal": "課題の目的",
          "improve": "改善したい特性",
          "worsens": "悪化する特性（技術的矛盾）",
          "ideal": "理想解（究極の理想結果）",
          "physical": "物理的矛盾（存在しない場合は null / 空）",
          "constraints": "制約事項",
          "resources": "利用可能資源",
          "evidence": "出典URL: ...\n取得日時: ...\n本文SHA-256: ...\n根拠: ..."
        }
      ]
    }
  }
  ```

## 9.3 必要な変換処理 (`app/triz_import.py` `export_item_to_values`)
1. **完全性の検証**: `verify_export_file(export_path, meta_path)` でメタファイルのSHA-256と実ファイルハッシュを照合。
2. **ドメイン検証**: `domain` が `DOMAINS` (`software`, `web_service`, `accounting_tax`, `logistics`, `creative`) に含まれるか検証。
3. **物理的矛盾の正規化**: `physical` が `None` / `false` / `""` の場合は空文字 `""` に正規化。文字列がある場合は切り詰めずに維持。
4. **定型人間チェック項目の付与**: `human_checks` に「【自動生成】...人が内容を確認済みであることを意味しません...」という定型文を付与（最大3000文字）。
5. **時間上限設定**: `max_seconds`（既定300秒、1〜900秒）を設定。
6. **課題セッション作成**: 親となる `agent-example` を `POST /api/projects/{pid}/agent-examples` で確保し、その配下の `learning/general` へPOST。

## 9.4 冪等性と検証方法
- **重複防止**: `GET /api/projects/{pid}/agent-examples/{eid}/learning/general` から既存セッションの `evidence` 内「`出典URL: ...`」を抽出し、同一URLが登録済みの場合はスキップ（`scripts/import_triz_problems.py` 115-120行目）。
- **検証手順**:
  1. Dry-run 検証:
     ```powershell
     python scripts/import_triz_problems.py --project <project_id> --dry-run
     ```
  2. 単体テスト実行:
     ```powershell
     pytest tests/test_triz_import.py tests/test_triz_general.py
     ```
  3. 実環境インポート:
     ```powershell
     python scripts/import_triz_problems.py --project <project_id>
     ```
