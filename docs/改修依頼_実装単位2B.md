# 改修依頼: 実装単位2B(P0-2/P0-3 アダプターへの接続)

## 背景
単位2A(`app/vehicle_reconciliation.py` の `reconcile_sources`、`app/vehicle_auto.py` の
`InvoiceDocument`/`AdapterResult`/`classify_invoice_relation`)は実装済み・456件合格。
今回は、これらの型・純粋関数を**実際の抽出処理(アダプター)に接続する**。
`docs/対応設計_最終版_2026-09-23.md` 第2.4節(アダプター側)、第3.3〜3.4節、依存関係の記述に従う。

## やること

### 1. `extract()` / `fuel()` の請求書(鑑)の扱いを変更
- 現行: `請求書(鑑)` は無条件 excluded。
- 変更後: `document_role='cover'` として `InvoiceDocument` を作り、明細計上はしないが、
  **請求総額の `source_total` control として保持する**(P0-2の独立合計の証拠)。
  無条件 excluded という判定そのものをやめる。

### 2. `fuel()` の戻り値を `AdapterResult` に変更
- 現行の `bool`(1行でも読めれば成功)をやめ、`AdapterResult`(`matched`, `records_added`,
  `parsed_total`, `printed_total`, `expected_detail_count`, `parsed_detail_count`, `complete`, `issues`)
  を返すようにする。
- `complete` の判定基準(設計書 第3.4節): 明細数と総額が原本表示と一致、または総額のみ存在し
  抽出明細合計と一致かつ未解析領域なし、またはvendor固有の終端検査を通過。1件でも読めた、だけでは complete にしない。
- 宇佐美: ブロック検出数を expected とし、sub/printed 欠落を issue化する。
- 太陽・車番別: 小計行の合計と明細加算の差を control として記録する。

### 3. `extract()` の重複判定を `classify_invoice_relation` に置き換え
- 現行の `(vendor, company, month)` キーだけの粗い除外をやめる。
- 各原本ファイルから `InvoiceDocument` を組み立て、同一 vendor/company/month の組で
  `classify_invoice_relation` を呼び、関係(`exact_duplicate`/`same_invoice_complement`/
  `different_invoice`/`partial_overlap`/`unknown`)に応じて処理する(設計書 第3.2節の優先規則どおり)。
- `partial_overlap` は自動除外せず確定阻害(issue化)。`different_invoice` は両方保持。
- `source_dispositions` に `duplicate_of`、`relation`、比較根拠を保存する。

### 4. Excel/CSV アダプターに control 抽出を追加
- Excel: 合計・小計・総計行、または費目別合計セルを `SourceControl`(`origin='source_total'`)候補にする。
- CSV: ファイル名月の請求合計列の総和は `origin='sum_of_lines'` とし、独立合計には使わない
  (別ファイルの鑑・PDF合計だけを `source_total` とする)。

## 制約
- **単位2Aの型・関数のシグネチャは変更しない。** アダプター側から呼び出すだけ。
- 既存の `test_csv_pdf_duplicate_is_not_double_counted` 等、現行の粗い除外を期待するテストは、
  設計書の新しい期待(別請求共存・完全重複・不完全差分)に合わせて更新する
  (設計書第3章「受入条件の検証方法」1〜8を参照)。既存の文字コード復元の二重加算防止試験は維持する。
- `app/vehicle_workflow.py` の合格判定(`validate_evidence`, `execute`, `goal_failures`)には、
  まだ**接続しない**(それは単位2C)。今回はアダプターが正しく control・AdapterResult・
  invoice関係を生成するところまで。
- `pytest -q` をプロジェクト全体で実行し、実測結果を報告する。
- 実装前に、変更するファイル・関数・更新するテストケースの一覧を示し、承認を得てから進める。
- 実行していないことを「できた」と書かない。
- 完了後、変更内容と試験結果を日本語で要約する。
