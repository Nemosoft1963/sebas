# 依頼: 修正提案の分析と対応設計(設計のみ。実装・配備・起動・外部送信は行わない)

## 背景
`docs/Local_Cowork_修正提案_2026-09-22.md` に、車両ごとの2026年1〜7月損益Excel生成システムの
修正提案がまとまっている。根拠として次の3文書も参照している(すべて `docs/` に配置済み):
- `docs/Local_Cowork_変更確認_2026-09-22.md`
- `docs/Local_Cowork_実装再監査_課題一覧_2026-09-20.md`
- `docs/Local_Cowork_UI進行復旧_改修設計案_2026-09-20.md`

対象コードは `app/vehicle_auto.py`、`app/vehicle_workflow.py`、`app/vehicle_profit.py`、
`app/vehicle_service.py`、`app/static/goal_review.js`、`app/static/artifact_shelf.js`、`app/web.py`、
`app/plan_feedback.py`、`app/goal_review.py`、`app/queue.py`(または類似名)、`app/project_manager.py`、
`app/automatic_triz.py`、`app/triz_general.py`、`app/executable_recipes.py` 等(実際のファイル名は
プロジェクト内を確認すること)。

## やること
1. 4文書すべてを読む。
2. 対象コードを実際に読み、修正提案の各項目(P0-1〜P0-3、P1-1〜P1-3、P2-1〜P2-2、記録の同期)について:
   - 提案の記述が現在のコードと一致しているか再確認する(古くなっている記述があれば明記)
   - 該当箇所(ファイル名・関数名・おおよその行番号)を特定する
   - 具体的な実装方針(どう直すか、どんなデータ構造・関数シグネチャの変更が要るか)を設計する
   - 受入条件をどう検証するか(テストケースの設計)を示す
   - 依存関係(どの項目を先に直さないと次が進められないか)を明らかにする
3. 提案書の「実施順序」(1〜5)を踏まえ、実装単位(1回の改修でどこまでやるか)に分割した
   実行計画を作る。P0(正確性)を最優先とすること。
4. 疑問点・提案書だけでは判断できない業務仕様(会計・配賦のルール等)があれば、
   実装せずに一覧化して報告する。

- **コードの変更・実装は一切行わない。設計書の作成のみ。**

- 実行していないことを「できた」と書かない。
- 完了後、設計書の要点を日本語で報告する。
