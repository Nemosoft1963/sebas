# セバス運用マニュアル：停止の見方・不足機能の提案・Jenkinsへの受渡し・自走・漏斗・分野パック

作成日: 2026-10-13　対象: 本番 LOCALSAPORTER（段階0〜4E 反映後）
位置づけ: 運用の手引き。**実案件で通しの運用をした実績はありません**（疑似PJの自動テストと、読み取りの確認まで）。最初の通し運用は、疑似PJで行ってください。

## 0. 全体の流れ（一枚で）

```
計画を作る → 外部評価（最大2回）→ 指摘 → 修正候補（被覆行列つき）→ 人が確定して適用 → ローカル再評価
      │
      └ どこかで止まったら ──→ 停止クラス（§1）が理由と次の一手を出す
                              ├ 機能が足りない（missing_capability）→ 不足機能の提案（§2）→ Jenkinsで開発（§3）→ 納品 → 再判定
                              ├ 人の判断が要る → 画面の案内に従って判断する
                              └ 安全境界（policy_block）→ 迂回しない。承認・権限の制御に従う
実行の進み具合は「漏斗」（§5）、分野ごとの型は「分野実行パック」（§6）、自動で進める範囲は「自走」（§4。既定は無効）
```

**大原則**: 承認・外部送信・公開・顧客連絡・RAG登録・完全削除は、どの機能も**自動では行いません**。不明・読み取り不能・エラーは、**通過扱いにされません**（「確認できず」「不足」「拒否」になります）。

## 1. 止まったとき：停止クラス

`GET /api/projects/{id}/stop-class`（読み取り専用）。`workflow-readiness` の応答にも `stop_class` が含まれます。

| クラス | 意味 | あなたがすること |
|---|---|---|
| `missing_binding` | 指摘・条件・工程の対応が不完全 | 保存済み材料での再対応付け（外部送信なし）。曖昧な指摘は候補を人が確定 |
| `missing_coverage` | 修正候補が指摘を覆いきれていない | 被覆表で未被覆の理由を見る。候補の再生成、または計画の整理 |
| `missing_decision` | 人が選ぶ以外に進めない | 計画承認、指摘の採否、業務事実の確認など。画面の案内に従う |
| `missing_evidence` | 操作や成果の証拠がない | 実行証拠・成果物・原本ハッシュの登録/確認 |
| `missing_capability` | 必要な操作を実行する機能が無い | §2（不足機能の提案）へ |
| `policy_block` | 安全境界による拒否 | **迂回しない**。次の一手は常に「なし」。承認・権限の制御に従う |

- **事前照合（不足機能）も停止の分類に反映されます**（2026-10-13の修正）。達成条件に必要な操作を実行する機能が無いPJでは、人の判断待ちや安全境界が無い限り、主たる停止が `missing_capability` になり、他の停止は `also` に残ります。応答の `preflight_status` が `ok` なら事前照合は正常、`unknown` なら事前照合が読めなかった状態で、**その場合も不足を隠さず、「不足なし」とは扱いません**。
- **自走への影響**: `missing_capability` が主の停止では、自走は進まず、停止クラスと次の一手を記録して止まります（被覆不足の修正候補の生成も、機能の問題が先に片付くまで行いません）。
- **分類できない停止は `missing_decision`**（推測で進めない）。複数の停止が重なるときは、`policy_block` > `missing_decision` > `missing_capability` > `missing_evidence` > `missing_coverage` > `missing_binding` の順で主たる1件と、他の一覧（`also`）を出します。
- **同じ停止が2回続くと、自動のランは止まります**（空転ガード）。新しい計画署名・新しい入力・人の選択があれば解除されます。

## 2. 不足機能の提案

### 2.1 いつ使うか
停止クラスが `missing_capability`、またはPJ概要に「不足機能 N件」が出たとき。**「0件」と「未確認」は別**です（未確認は事前照合を実行していない状態）。

### 2.2 流れと操作
| 段階 | 操作（画面：PJ概要の「不足機能」） | API |
|---|---|---|
| ① 事前照合・提案の作成 | 「不足機能を確認する（ローカルで作成）」 | `POST /api/projects/{id}/capability-gaps/propose`（`actor`）。結果は `GET .../capability-gaps` |
| ② 内容の確認 | 提案の詳細を読み、「確認済みにする」（担当者・理由） | `POST .../capability-gaps/proposals/{proposal_id}/review`（`actor`/`reviewer`、`reason`） |
| ③ 指示の作成 | 「Jenkins指示を作成」 | `POST .../proposals/{proposal_id}/export`（`actor`）。`development_instructions/<proposal_id>/` に3ファイルを出力 |
| ④ Jenkinsへ渡した記録 | 「Jenkinsに渡した（記録）」（§3 の後） | `POST .../proposals/{proposal_id}/submitted`（`actor`、`memo`） |
| ⑤ 納品の取込み | （API） | `POST .../proposals/{proposal_id}/delivery`（`actor`、`delivery`） |
| ⑥ 再判定 | 「再判定」 | `POST .../proposals/{proposal_id}/verify`（`actor`） |

- 状態: `draft → reviewed → export_ready → submitted → delivered → verified`（`rejected`／`stale`／`needs_evidence` もあります）。**「指示を作成済み（export_ready）」「納品された（delivered）」「検証済み（verified）」は別の言葉**で、`verified` は ⑥ の再判定でしか付きません。
- **提案は、入力不足・安全境界・対応付け不備・証拠不足からは作られません**（それらは別の対応が先です）。同じ不足から提案が増えることもありません（同一の案件・署名・条件・能力・不足は1件）。
- 提案の**受入テスト**は、達成条件の短い引用と操作名を含む具体的な検証項目です（実行ログと成果物ハッシュの登録、外部送信0、再生で不足が消えること、安全ゲートを迂回しないこと）。先頭は従来どおりの識別子（`accept:<操作>:<種別>`）です。
- 提案・指示には、秘密や個人情報、原本の本文全文は入りません。入りそうなときは出力が拒否されます。

### 2.3 `verified` の意味
**Jenkinsの成功表示やテスト成功だけでは、能力は有効になりません。** ⑥ の再判定は、納品された実装を**人が本番へ反映した後の現行コード**で、元の案件・同じ入力の事前照合を再生し、**元の不足が消えたときだけ** `verified` にします。不足が残れば `delivered` のままで、残りの理由が出ます。計画の署名が変わっていれば `stale` です。

## 3. Jenkinsへの受渡し（ジェンキンス = http://localhost:8012）

セバスとジェンキンスは**直接つながっていません**。人が、ファイルを運びます。ジェンキンス側には「橋渡し」のAPIがあり、**セバスへは接続も送信もしません**。

### 3.1 手順
1. **セバスで指示を作成**（§2.2 ③）。出力先は、そのPJの作業領域の `development_instructions/<proposal_id>/`（`instruction.json`、`REQUEST.md`、`manifest.json`）。
2. **ジェンキンスへ取り込む**: 3ファイルの全文を送ります。
   `POST http://localhost:8012/sebas/intake`（JSON: `instruction_json`、`request_md`、`manifest_json`）
   - SHA-256、スキーマ、**変更禁止境界**（`.env`、`/data`、compose、プロキシ、安全ゲート）の有無、受入テストの有無を検査します。改ざん・欠落は **422 で拒否**。同一内容の再投入は冪等、別内容は上書きしません。
   - 確認: `GET /sebas/intake/{proposal_id}`
3. **隔離した作業コピーを作る**: `POST /sebas/intake/{proposal_id}/prepare`（JSON: `source_project`＝コピー元（既定 `LOCALSAPORTER`）、`start`、`backend`）
   - **基準版が一致するときだけ**作ります。ジェンキンスの作業コピーが本番とずれていれば **409（再同期が必要）**。先に本番→作業コピーの同期をしてください。
   - `.env`・データ・`.git`・`.venv` はコピーしません。`start=true` なら、**承認つき**でセッションを開始します（書込み・実行は人の承認が必要）。
4. **実装**: ジェンキンスのセッションで、作業コピーに実装させます（承認しながら進める）。
5. **納品データを作る**: `POST /sebas/intake/{proposal_id}/delivery`（JSON: `test_args`＝pytestの引数（空なら全体）、`run`）
   - 差分とテスト結果から、**セバスの納品の形式の `delivery`** を返します。変更禁止領域への変更や、変更なしは **422 で拒否**。
6. **セバスで記録**: §2.2 ④ → ⑤（返ってきた `delivery` を `delivery` に渡す）→ ⑥。
7. **人が本番へ反映**: ジェンキンスの作業コピーの差分を確認し、本番へ反映（差分ZIP方式）してから、⑥の再判定を行います。

### 3.2 気をつけること
- 基準版は、`app/*.py` の内容ハッシュから作ります。**本番を更新したら、ジェンキンスの作業コピーも同期**してください（ずれていると 409 / `stale`）。
- 納品の `base_commit` には、基準版（`app-content-…`）が入ります。成果コミットは作業コピーのgitのコミットIDです。
- 作業コピーは `プロジェクト名__<proposal_idの先頭12文字>` という名前で作られます。不要になったら、手動で削除してください。

## 4. 自走（既定は無効）

`GET /api/projects/{id}/autopilot`（状態・設定・直近のティック。読み取り専用）、`POST .../autopilot/enable`・`/disable`（`actor`、`reason` が必須）、`POST .../autopilot/tick`（`actor`、`dry_run`）、`POST .../autopilot/run`（`actor`、`max_ticks`≦10）。

- **許可される作業は6つだけ**: 保存済みレビューの再対応付け、ローカルの修正候補の生成、被覆行列の更新、事前照合、完了判定の読み取り、停止クラスの記録。いずれも可逆なローカル作業です。
- **自動では行わない**: 計画承認、候補の本適用、外部送信、公開、顧客連絡、RAG登録、OCR結果の計算投入、完全削除、Jenkinsへの送信。許可リスト外は拒否され、監査に残ります。
- 人の判断が要る停止（安全境界・判断待ち・機能不足・証拠不足）では**進まず**、停止クラスと次の一手を記録して止まります。
- 外部呼出・評価ラウンド・予算が1つでも増えたティックは**失敗**で、以降の自走が止まります。
- **定期実行はありません**。人がAPIを呼んだときだけ動きます。有効にする前に、必ず `dry_run` で何をするかを確認してください。
- 候補の生成は、ローカルAI（Ollama）で行います。**実際のOllamaでの生成の質・所要時間は、実案件では未確認**です。失敗（未起動・タイムアウト・不正な出力・検査不合格）は、ティックの失敗として理由つきで記録され、成功扱いにはなりません。

## 5. 実行の漏斗（読み取り専用）

`GET /api/projects/{id}/execution-funnel`、全PJの集計は `GET /api/execution-funnel`。PJ概要にも表示されます。

「計画合格 → 計画承認 → 工程実行 → 証拠検証 → 達成条件」の5段を、**証拠のある段だけ**数えます。
- 「**証拠未確認**」: 状態は「済」だが、証拠が確認できない。
- 「**確認できず**」: 読み取れなかった。通過には数えません。
- 構造合格だけ・外部評価が `unverifiable` の計画は、計画合格に数えません。外部作用の工程は、登録された外部証拠が無ければ実行済みに数えません。

## 6. 分野実行パック（汎用3種。記録のみ）

`GET /api/domain-packs`、`GET /api/projects/{id}/domain-packs`、`GET .../domain-packs/{domain_id}/conformance`、`POST .../domain-packs/select`・`/clear`。画面はPJ概要の「分野実行パック」。

- 汎用パックは `document_evidence.v1`（原本引用つきの文書生成）、`table_processing.v1`（表データの確認と加工）、`public_research.v1`（許可された公開調査）。権限境界はすべて不許可。
- 候補が決まっても**自動では選ばれません**（同点・該当なし・確認できず）。選ぶのは人で、**記録のみ。計画・工程・実行は変わりません**。
- 適合検査の「確認できず」は適合に数えません。適合していないパックを選ぶときは、警告を確認してください。
- **「適合」の意味に注意**: 適合検査の「適合」は、**工程がパックの宣言（実行器・権限境界・証拠契約）に合う**という意味で、**達成条件を満たせるという意味ではありません**。画面には、事前照合の不足機能の件数が併記されます（取得できないときは「確認できず」）。
- パックを選ぶと、事前照合の結果に `domain_pack`（適合の件数、実行器の5状態の実測）が加わります。**パックを選んでも、不足は減りません**（宣言は実証の代わりになりません）。

## 7. 削除状態の安全化

論理削除の状態を確認できないとき（DBの破損など）、そのPJは**削除済みと同様に扱われ**、操作が止まります（API は 410）。PJ一覧には残り、`delete_state_unknown: true` が付きます。**このフラグが付いたら、削除状態のDB（記憶DBのファイル名に `.delete.sqlite3` を付けたもの）の調査**が先です。

## 8. 既知の限界（正直に）

- **実案件での通し運用は未実施**です。疑似PJの自動テストと、読み取りAPI・画面の確認までです。
- 事前照合の操作の語彙はキーワード方式です。語彙外の達成条件は「不明」として人の確認に回ります。実際の文面で意図どおりに分類されるかは、運用しながら確認してください。
- 既存のPJ（車両損益・販売など）向けのパック化と、パックによる実行の振り分けの切り替えは、行っていません。
- 確認者名は**本人認証ではありません**（作業記録用の名前）。通信は**TLSなし**です。
- 本番の全体テストには、Windows固有の既知の失敗が3件あります（バックアップ時のファイル数の不一致2件、子プロセスの文字コード1件）。
- Jenkinsの橋渡しAPIは、認証がありません（ジェンキンスのほかのAPIと同じ）。ローカルでの利用を前提にしています。

## 9. 困ったとき

| 状況 | 見るところ |
|---|---|
| 何で止まっているか分からない | `GET .../stop-class`（クラス・コード・理由・次の一手） |
| 提案が作られない | 停止クラスが `missing_capability` か。入力不足・安全境界・証拠不足なら、提案は作られません |
| 指示を作成できない | 提案が `reviewed` か。秘密・個人情報らしい文字列が含まれていないか |
| ジェンキンスへの取込みが 422 | 3ファイルを改変していないか（SHA-256）。変更禁止境界・受入テストが欠けていないか |
| 作業コピーの作成が 409 | 基準版のずれ。本番→ジェンキンス作業コピーの再同期 |
| 納品が `stale` | 基準版のずれ、または計画署名の変更。再同期して再評価 |
| 納品が `rejected`／`needs_evidence` | ハッシュ不一致、テスト失敗・欠落・0件、成果物の内容なし |
| 再判定しても `verified` にならない | 実装を本番へ反映したか。反映後の現行コードで、元の不足（5状態）が解消したか |
| 自走が止まった | `GET .../autopilot` のティック履歴（失敗の理由、空転ガード）。有効化し直す前に原因を確認 |
| 画面に「確認できず」が出る | 読み取りに失敗しています。通過扱いではありません。原因（DB・応答）を調べてください |
