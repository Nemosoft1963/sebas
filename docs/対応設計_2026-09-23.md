## 1. P0-1 金額の欠損・読取失敗・実額ゼロの分離

### 現状再確認

提案・再監査の中核は現行コードと一致する。未修正。

原因の連鎖:

1. `app/vehicle_auto.py` `text()`（16–17行）: `str(value or '')`。数値 `0` は falsy なので空文字になる。
2. `money()`（24–31行）: 空は正規表現不一致で `None`。文字列 `'0'` / `'0.0'` は 0 を返す。よって **数値0は欠損扱い、文字列0は実額**。
3. `Extractor.add()`（122–139行）: `amount is None` のとき、数式キャッシュ欠落（`formula_gaps`）なら `kind='read'` を出すが、**通常の非数値・空・数値0由来の None は return するだけ**。明細も確認事項も残さない。
4. `finish()`（315–331行）: `zero=True`（案件文に「不足…0円」があるとき `authorized_zero()`）なら、配賦済み実額の無い車両×月×費目へ `quality='assumed_zero'`、`source_ref='policy:missing-zero'` を補う。黙って捨てた読取失敗も「対象明細なし」と見なされ仮定0円になる。
5. `evidence_issues()`（393–400行）: 未解決 issue と仮定ゼロ方針と原本参照だけ。読取失敗が issue に無い限り検証を通す。
6. `vehicle_profit.calculate()` は `quality` を `actual|estimated|missing|assumed_zero` に限定。読取失敗用の区分が無い。

CSV燃料だけは例外で、金額欄が `None` なら issue を出して continue する（240–243行）。Excel台帳・給与・汎用台帳は黙って捨てる。経路で品質が違う。

数式セルのキャッシュ無しは `formula_gaps` で issue 化済み（`tests/test_vehicle_auto.py` `test_formula_without_cached_value_is_not_silently_treated_as_absent`）。これは維持する。一方、非数式の「要確認」や数値0は既存試験が検出していない、という再監査の指摘は現行試験でも正しい。

`triz_common.validate_problem` の None 修正は本不具合と無関係（変更確認どおり）。

古くなっている点: 再監査が `money` 単体の16行を根拠にしたこと。本質は `text()` の falsy 変換。`money` だけ直しても、他が `text(0)` を使うと同じ罠が残る。ただし `text()` のグローバル変更は車番・会社名にも影響するため、金額経路を先に分離する。

### 設計方針

金額の解釈結果を4分類し、相互に変換しない。

| 分類 | 入力例 | 保存 | 不足0円方針 | 確定完了 |
|---|---|---|---|---|
| 実額（非ゼロ） | `1000`, `'1,000円'` | `quality='actual'`, amount=整数 | 適用しない | 他条件次第 |
| 実額ゼロ | `0`, `'0'`, `0.0` | `quality='actual'`, amount=0, 原本セル参照必須 | 適用しない | 他条件次第 |
| 真正の欠損 | 空セル、空白のみ | レコードを作らない。当該車両×月×費目が空なら不足0円方針時のみ `assumed_zero` | ここだけ適用 | 方針無なら未確定 |
| 読取失敗 | `'要確認'`, `'—'`, 非数値、計算値の無い数式 | 明細に入れない。`issues` に `kind='read'`、原本セル・生値・理由 | 適用しない | 阻止 |

実装の要点:

- **`parse_money(value) -> MoneyParse` を新設**（`money()` の置換または薄いラッパ）。  
  シグネチャ案:

  ```python
  # status: 'amount' | 'blank' | 'unreadable' | 'out_of_range'
  # amount: int | None
  # raw: str  # 正規化前の表示用
  def parse_money(value) -> dict: ...
  ```

  - `int`/`float`/`Decimal`（`bool` 除外）は文字列化せず数値として扱う。`0` は `status='amount', amount=0`。
  - 文字列は現行のカンマ・円・¥除去のあと、空なら `blank`、正規表現不一致なら `unreadable`。
  - 既存 `money()` は移行期間中 `parse_money` の amount だけ返す互換にできるが、呼出し側を `parse_money` へ切り替える。黙って `None` を返す経路を残さない。

- **`text()` は当面維持。** 金額以外（氏名、車番）で `0` を空にする害は小さい。金額は `parse_money` が `text()` を通さない。

- **`Extractor.add()` の変更:**
  - 引数 `amount` を「整数 or MoneyParse」にせず、呼出し側で分岐する方が安全。
  - `status='unreadable'`: `issue('read', ..., raw=..., reason=...)` して return。レコードを作らない。
  - `status='blank'`: レコードも issue も作らない（真正欠損。finish の不足0円が判断）。
  - `status='amount'`: 現行どおりレコード。`amount==0` でも `quality='actual'`。`if not allocations and amount:` はゼロ円でも配賦不要（帰属先が1台なら既存どおり ratio=1）。複数候補で0円のときは issue を出すか（業務確認、第4章）。

- **`finish()`:** 不足0円補完の `present` 判定に、同一車両×月×費目の **読取失敗 issue** がある場合は補完しない。issue が残れば `evidence_issues` が確定を止める。

- **`vehicle_profit.calculate()`:** 新 quality を増やさず、読取失敗は records 外の issues に置く。既存算術エンジンを壊さない。Excel「不足と未配賦」は既に `auto_extraction.issues` を出している（`build_workbook`）ので、読取失敗がここに出る。

- **CSV燃料:** 既に unreadable を issue 化している。`parse_money` 導入後も同様。空欄行は blank としてスキップし、0円行は実額ゼロ。

REVISION を上げる（例: `20260923.1`）。`prepare()` / `execute()` は extractor_revision 不一致で再抽出する既存機構を使う。

## 2. P0-2 原本と出力の独立した金額照合

### 現状再確認

提案どおり未修正。再監査の再現条件はコード上いまも成立する。

- `Extractor.finish()` 331行: **常に `source_controls=[]`**。

- `execute()` 284行: `checks['source_controls']=not validate_evidence(...)`。自動経路で issue が空なら **空の controls でも True**。
- `goal_failures()` 必須キーに `source_controls` がある（199行）が、上記 True で通過し得る。
- `vehicle_profit.build_workbook()` の `independent_profit_match` は **正規化入力を Python と LibreOffice で再計算した一致**。抽出漏れの否定ではない（提案・再監査と一致）。
- 手動入力経路（`tests/test_vehicle_workflow.py` `test_evidence_rejects_unknown_source_unreadable_and_control_mismatch`）は controls 不一致を検出する。自動経路に同等が無い。

「原本別・会社別・月別・費目別の独立合計」を取る処理は存在しない。請求書鑑は P0-3 で除外され、合計証拠としても使われない。

### 設計方針

照合を3層に分け、自動経路でも手動経路と同じ第2層を必須にする。第3層が無いものを照合済みと呼ばない。

1. **入力内訳照合（既存）:** 明細金額 = 配賦 + 未配賦。`calculate()` の reconciliation。抽出漏れは分からない。
2. **取込合計照合（手動経路に既存、自動へ拡張）:** 同一 `source_ref × month × category × tax_basis` の明細合計 = `source_controls[].amount`。locator 必須。
3. **独立原本合計（新規必須）:** 明細を足した値ではない。原本上の合計行、請求総額、鑑の請求額、CSVの合計欄など **別セル/別文書** から取得した値。取得不能は `status='unavailable'` であり合格ではない。

データ構造（`source_controls` を拡張、空配列を合格にしない）:

```python
{
  "source_ref": "context:<id>",
  "month": "2026-01",
  "category": "fuel",          # 不明なら null ではなく category='unknown' + issue
  "tax_basis": "inclusive",
  "amount": 12345,             # 独立に読んだ整数。読めなければこのオブジェクトを作らず control_unavailable issue
  "source_locator": "請求書(鑑)!B20",
  "origin": "source_total",    # 'source_total' のみ独立照合として認める。'sum_of_lines' は不合格
  "included_amount": 12000,    # 取込明細合計
  "excluded_amount": 0,        # 根拠付き除外
  "unallocated_amount": 345,
  "delta": 0,
  "status": "matched"          # matched | mismatch | unavailable
}
```

`finish()` / 新規 `build_source_controls(ex, docs)`:

- Excel: 合計・小計・総計行、または費目別合計セル。車両番号列が合計語の行は既に車両化していない。その行の金額を control 候補にする。
- CSV: ファイル名月の請求合計列の総和は **明細合計** なので origin を `sum_of_lines` とし、独立合計には使わない。別ファイルの鑑・PDF合計を `source_total` にする。
- PDF鑑: P0-3 と同時に、除外せず `origin='source_total'` の証拠として読む。
- 独立合計が1件も作れない原本は `issue('control', ..., '照合不能')`。disposition は included のまま確認待ち。

`validate_evidence()`:

- `auto_extraction` 分岐を廃止し、共通の controls 検査へ合流。そのうえで自動特有の `evidence_issues` を追加。
- `origin!='source_total'` の controls だけでは `checks['source_controls']` を True にしない。
- controls 空 → 必ず issue「独立した原本合計を取得できない」。
- delta≠0 → mismatch。除外根拠が `source_dispositions` または `excluded_records` で説明でき、かつ独立合計 = 取込 + 除外 + 明示未対象、のときだけ matched。

`execute()` 284行の `not validate_evidence(...)` は残してよい。中身が空配列合格をやめる。

暫定Excelは生成してよい（既存 `needs_review`）。確定は `status='completed'` かつ全 control が matched。これが提案の「暫定と確定の区別」。

`extract()` 334–345行付近:

- キーは `(vendor, company, month)`。vendor はファイル名の wing/eneos または 宇佐美/御買上明細/請求明細。
- CSVを先に処理し、キーを `csv_keys` へ。
- **`請求書(鑑)` を無条件 excluded**。または PDF かつ同一キーの CSV がある場合 excluded。
- 除外 evidence 文言は「照合参照として保持」だが、実際は dispositions のみで controls に載らない。

`fuel()` 戻り値は `len(self.records)>start`。1行でも読めれば成功。宇佐美PDFは `if not sub or not printed: continue` でブロックを黙って飛ばす（261–280行）。太陽・車番別集計もマッチ行だけ加算。

### 設計方針

請求の同一性を、業者・会社・月の3点セットから、次の指紋へ変更する。

```python
invoice_identity = {
  "vendor": "usami"|"wing"|"taiyo"|...,
  "company": "弘和"|"関東"|...,
  "month": "2026-01",
  "invoice_no": str | None,
  "gross_total": int | None,     # 独立合計
  "line_fingerprint": str,       # 正規化した (hint, amount) の多重集合ハッシュ
}
```

判定:

| 関係 | 操作 |
|---|---|
| 指紋一致（番号または明細集合+合計） | 後着は excluded。disposition evidence に先行 source_ref。二重加算しない |
| 同一キーだが明細が真部分集合 | 部分抽出。差分を `kind='partial_extract'` issue。成功扱いにしない。多い方を正、欠け側は照合待ち |
| 同一業者・会社・月で指紋不一致 | **別請求として両方保持** |
| 鑑のみ（明細なし、合計あり） | excluded ではなく `role='control'`。P0-2 の source_total。明細PDF/CSVと対にする |
| 部分行だけパース成功 | `fuel()` は「期待ブロック数 vs 成功ブロック数」を返し、不足なら issue。`True` を全体成功にしない |

`fuel()` シグネチャ変更案: `-> dict`（`parsed_lines`, `expected_lines`, `invoice_no`, `gross_total`, `complete: bool`）。`extract()` が complete でない PDF を csv_keys の除外条件に使わない。

宇佐美: ブロック検出数を expected とし、sub/printed 欠落を issue。太陽・車番別: 小計行の合計と明細加算の差を control。

請求番号が原本に無い形式は `invoice_no=None`。その場合は明細集合+合計のみ。どちらも取れない場合は重複判定不能 issue を出し、除外しない（二重の恐れを隠さない）。

### 変更対象ファイル

- `app/vehicle_auto.py`: `extract`, `fuel`, 必要なら vendor 判定
- `tests/test_vehicle_auto.py`: 既存重複試験の期待を更新し、別請求共存・完全重複・不完全差分を追加

### 受入条件の検証方法

1. **同月別請求:** 同一会社・月・宇佐美で合計も明細も異なるPDF/CSV 2件。レコードが両方残る。excluded にしない。
2. **完全重複:** 同一明細CSVと同一内容PDF。一方 excluded。燃料合計は一回分。disposition に相手 ref。
3. **不完全CSV+PDF:** CSV 1行、PDFは2車番。部分抽出 issue。確定阻止。差分車番が issue または未取込として見える。
4. **鑑:** ファイル名に `請求書(鑑)`、合計のみ。明細ゼロでも adapter 失敗にせず、control として合計が残る。無条件 excluded にしない。
5. **部分ブロック:** 宇佐美風テキストで2ブロック中1つだけ小計あり。1件は取込、1件は read/partial issue。`fuel` 成功で全体完了にしない。

## 11. 提案書だけでは判断できない業務仕様（実装しない）

実装に入る前に人間確認が必要な項目。推測で埋めない。

1. **不足0円方針の対象費目:** 全 CATEGORIES か、高速・その他など一部か。現行は全費目に仮定ゼロを撒く。
2. **実額ゼロの配賦確認:** 金額0で車両候補が複数のとき、確認するか無視するか。

12. **確定完了の人間確認:** 機械照合合格後も人間の3チェック必須か（現行 RAG は必須）。提案の確定と RAG を同一視してよいか。
