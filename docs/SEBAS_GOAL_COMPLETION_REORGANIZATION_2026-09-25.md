# セバス 目標達成型システムへの全体再整理と過不足提案

- 作成日: 2026-09-25
- 対象: LocalSAPOTER（呼称: セバス）
- 文書区分: 現状監査・次期改修提案
- OCR: 改善工程は終了済み。今後は既知不具合の修正と回帰防止のみとし、新規改善対象から外す。

## 1. 結論

セバスには、目標設定、構造化計画、ローカルLLM実行、外部AIによる計画検証、人間承認、成果物検証、承認済みRAG、TRIZ回復、車両別月次損益、OCR、進行状態UIまで、目標達成に必要な部品がほぼ揃っている。

中心課題は機能不足ではない。各機能が別々の状態、版、判定、画面操作を持ち、「目標を達成するまで次の行動を選び続ける単一の制御系」に統合されていない。このため、個別機能が正常でも入力不足、外部検証待ち、業務事実待ち、暫定成果などで止まり、「先へ進まない」「目標未達なのに終了した」と見える。

次期改修では既存機能を次の閉ループへ統合する。

> 目標契約 → 達成条件分解 → 計画被覆検査 → 実行 → 証拠収集 → 独立検証 → 未達差分判定 → RAG/TRIZ/再計画 → 再実行 → 人間確認 → 確定完了

## 2. 現状

### 稼働状態

2026-09-25時点で統合フロント、Ollama、Open WebUI、Computer、Google Publisher Browser、ワークスペースは稼働し、`scripts/healthcheck.ps1` は全項目PASS。ローカルLLMは `mistral-small3.2:24b-instruct-2506-q4_K_M`。保存済み最新検証は本番イメージ内656テスト合格である。今回の監査では稼働イメージにpytestがないため再実行できず、healthcheckのみ再確認した。

### 実装済み

| 領域 | 現在の機能 | 評価 |
|---|---|---|
| 目標・計画 | 目標、達成条件、制約、構造化タスク、依存関係、最終検証 | 達成条件の分解品質に弱点 |
| 計画検証 | 版ハッシュ、外部AI検証、指摘取込、修正案、人間承認 | 停止経路と操作が多い |
| 実行 | タスク依存、成果物、再開、詳細工程、安全な限定実行 | 実行器が複数系統 |
| 完了判定 | 成果物検査、最終検証、車両損益の独立照合、暫定/確定 | 全領域共通の完了定義が不足 |
| RAG | 人間承認、期限、取消、証拠・入力版照合、project隔離 | 次行動選択への統合が弱い |
| TRIZ | 診断、候補、再現・転用試験、採用、限定再実行、取消 | 通常の回復制御とUI接続が弱い |
| 車両損益 | 原本抽出、月次計算、Excel、独立照合、配賦確認 | 基準ワークフローにできる |
| OCR | 実行、証拠、レビュー、公開、RAG登録・取消 | 改善終了。入力サービスとして固定 |
| UI | 停止理由、次操作、ボタン可否、成果物棚 | 説明はできるが完走制御ではない |

### 稼働案件で確認した問題

「車両別評価データの作成」は計画版25、4タスク、status `ready`。統合進行状態は `accuracy_blocked` で、原本統制値不足、未配賦225件、照合 `unavailable` のため確定できない。OCR読取未解決は0件であり、停止原因はOCRではない。

長い目標本文に対して保存された成功条件は1件だけである。車両別・月別、給与、会社負担社会保険、税込リース注記、月別燃料、車番対応、車両別シートなどが、機械判定可能な独立条件として保持されていない。入口の目標契約が粗いと、後段の厳格な検査だけでは正しい完了制御ができない。

統合進行APIは停止理由を返すが、次アクションのendpointは空で、UIは既存ボタンを活性・非活性にする方式である。状態説明はできても、セバス自身が安全に次工程を連続実行する制御にはなっていない。

## 3. 過剰・重複

1. mission、task、goal review、revision、queue、job、workflow readiness、vehicle workflow、TRIZ、RAGが別々の状態を持つ。
2. task完了、mission completed、成果物生成、検証合格、人間承認、RAG登録、TRIZ adopted、business recoveredで「完了」の意味が異なる。
3. 指摘取込、修正案、反映、送信承認、外部検証、計画承認、実行開始が独立操作で、低リスクのローカル処理にも操作が増える。
4. 概要文書、BUILD_REPORT、CHANGELOG、再開記録、コードの版が分散し、古い文書から完了済み機能を再提案する危険がある。
5. ルートにGit管理情報がなく、`git status` と `git log` を実行できなかった。別の正本リポジトリがあるなら稼働ソースとの対応manifestが必要。

共通語彙を `produced`、`verified`、`accepted`、`achieved`、`learned` に固定し、単独の `completed` は互換表示へ縮小する。

## 4. 不足機能

### P0-1 単一のGoalContract

目標を固定構造で保存し、計画・実行・検証の親にする。

- goal_id、version、hash
- objective、scope、exclusions、constraints
- acceptance_criteria
  - criterion_id、statement、test_method、required_evidence、human_decision_required
- source_versions
- completion_policy

自然文が長いのに条件が少なすぎる場合は計画前に停止し、ローカルLLMが候補分解と原文対応表を作る。人間へ白紙質問を返さない。条件の削除・統合だけ明示確認する。

### P0-2 計画被覆表

全達成条件を少なくとも一つの実行タスクと検証へ対応付ける。

| 達成条件 | 実行タスク | 入力 | 成果物 | 検査 | 実操作証拠 | 状態 |
|---|---|---|---|---|---|---|

対応のない条件、検証だけで実行がない条件、成果物だけで実操作証拠がない条件は計画承認不可。外部AIには計画全文より、この被覆表と公開可能要約を検証させる。

### P0-3 単一状態機械

正本状態を次に限定する。

`draft → clarifying → planned → plan_review → plan_approved → executing → verifying → needs_input | needs_approval | recoverable_failure | development_required → achieved | failed | cancelled`

RAG、TRIZ、外部AI、OCR、車両計算は状態ではなく、次アクションを実行する能力として扱う。

### P0-4 共通Completion Gate

`achieved` は次の全条件を満たす場合だけ許可する。

1. 全criterionがPASS。
2. 必須成果物の存在、ハッシュ、内容検査がPASS。
3. 必須の実操作証拠が存在。
4. 入力原本の版が検証時から不変。
5. 未解決の読取、配賦、差額、業務事実、開発阻害が0。
6. 必須の独立照合がPASS。
7. 必須の人間承認が対象版へ結び付く。

未達なら成果物があっても `produced` または `verified` に留め、理由コードと根拠パスを残す。

### P0-5 Next Action Controller

現在のreadiness表示を、次の1件を選び実行する制御器へ発展させる。

1. GoalContractと証拠を再評価。
2. 未達criterionを優先順に並べる。
3. 実行可能な最小アクションを選ぶ。
4. ローカルで安全な処理は自動実行。
5. 外部送信、公開、配賦判断は具体的差分と影響を示して承認待ち。
6. 実行後に必ずGoalContractを再評価。
7. 同一失敗の無限反復を回数、時間、費用上限で停止。

次操作は必ず action_id、endpoint、入力schema、許可・禁止理由、冪等キーを持たせる。

### P1-1 証拠グラフ

原本、抽出値、変換、計算行、成果物セル、検査、承認を追跡可能にする。車両損益では各「車両×月×費目」の値から原本ページ・行、採用ルール、配賦回答、計算式へ戻れることを受入条件にする。

### P1-2 人間確認の最小化

質問は未達条件を閉じるための業務事実に限定し、次を同時表示する。

- 何が不明か
- どの達成条件が止まるか
- 原本から確認できた事実
- 推奨候補と計算影響
- 回答後に自動再実行する範囲

一度回答した事実は適用条件と版が一致する限り継承する。金額そのものは一般化しない。

### P1-3 統一回復方針

1. 入力・業務事実不足: 最小質問。
2. 既知不具合: development_required。TRIZへ逃がさない。
3. 承認済みRAGに同一条件の手順: 適用検査後に限定再利用。
4. 一時失敗: 安全な再試行。
5. 未知の方法不足・反復失敗: TRIZ。
6. TRIZ候補: 再現と転用の両試験合格後だけ限定採用。
7. 回復後: 元criterionを再検証し、business_recoveredだけ成功。

TRIZはユーザーへ発明を丸投げせず、候補、試験、影響、採否を提示する回復エンジンにする。

### P1-4 再開の自動化

再起動後に正本台帳から次アクションを再計算する。残留runningジョブは成果物、ロック、checkpointを検査して executing、recoverable_failure、needs_inputのいずれかへ収束させる。

### P1-5 UI一本化

主画面を次の五つに絞る。

1. 目標と達成条件
2. 現在地と停止理由
3. 次にセバスが行うこと
4. 人間に必要な判断
5. 成果物と達成証拠

RAG、TRIZ、外部AI、OCRは詳細へ残し、通常利用者に工程選択を要求しない。進捗はタスク件数でなく、重み付きcriterion PASS率と証拠充足率で表示する。

### P2 評価と版管理

記録指標:

- 誤ったachieved判定 0件
- 目標要求保持率 100%
- criterion計画被覆率 100%
- 自動完走率
- 人間質問数
- 同一原因の再停止回数
- RAG・再試行・TRIZ別回復成功率
- 原本まで追跡できる値の割合
- 再起動後の自動復旧率

`CURRENT_SYSTEM_STATE.json` と `CURRENT_SYSTEM_STATE.md` を機械生成し、コード版、稼働イメージ、機能フラグ、最新テスト、未達案件、次期計画を一元化する。

## 5. 車両別月次損益を基準シナリオにする

達成条件を少なくとも次へ分解する。

1. 対象会社・期間・車両が確定。
2. 全車両について全対象月の行が存在。
3. 売上、燃料、リース、人件費、会社負担社会保険、その他費目が定義済み。
4. 給与と社会保険が承認済み車両配布ルールで集計。
5. 燃料費が月別原本と車番対応に基づく。
6. リース額を保持し、税込であることを明記。
7. 車両別月次損益と会社合計を生成。
8. 車両ごとのシートを生成。
9. 元帳、請求単位、配賦前後、会社合計の独立照合がPASS。
10. 未配賦、読取失敗、照合不能、根拠不明が0。
11. Excel再計算が可能で数式エラー0。
12. 主要金額を原本まで追跡可能。

未配賦225件は、原因、金額影響、対象月・人・車両、既回答36項目で解消可能かを自動分類する。既回答を先に適用し、残る業務判断だけを質問する。

## 6. 外部AI・RAG・TRIZの役割

- 外部AI: 独立批評者。criterion_id、問題、重大度、根拠、修正案、必要能力を構造出力し、セバスが採否と理由を保存する。
- RAG: 承認済み手順の候補検索。project、入力版、適用条件、証拠、期限、取消を毎回再検査し、適用後に元criterionを再検証する。
- TRIZ: 未知の方法不足または反復失敗の発明経路。既知不具合、入力不足、業務判断不足には使わない。候補生成だけで終了しない。

## 7. 実装順序

### 第1段階: 完了定義

GoalContract、要求保持検査、計画被覆表、共通Completion Gateを実装し、既存状態を変換する。長い目標を1成功条件へ縮約せず、未達ならachievedにならないことを受入条件とする。

### 第2段階: 完走制御

目標実行台帳、イベント履歴、Next Action Controller、ローカル処理の自動連鎖、承認点停止、冪等再開を実装する。

### 第3段階: 証拠と回復

証拠グラフ、統一回復方針、最小質問、回答後限定再実行、再起動時の自動収束を実装する。

### 第4段階: 車両損益完全受入

12条件へ再分解し、回答済み36項目を適用、未配賦225件を分類、残質問を最小化する。全車両・全月、未解決0、独立照合PASS、人間確認済みのときだけachievedとする。

### 第5段階: 整理

現状文書の自動生成、重複画面・旧状態判定の段階廃止、指標ダッシュボード、基準シナリオ回帰、release manifestを整備する。

## 8. 対象外

- OCRの追加改善
- モデル交換による構造問題の代替
- 外部AIへの全面委任
- 未承認の金額・料率・配賦の推測
- TRIZ候補の無検証採用
- Docker、Ollamaモデル、履歴、原本の初期化

## 9. 推奨する次の開発単位

最初は「GoalContract・計画被覆表・共通Completion Gate」に限定する。その後readinessをNext Action Controllerへ変更する。この順序なら既存のOCR、車両損益、RAG、TRIZ、外部AI検証を捨てず、一つの目標達成ループへ接続できる。

## 10. 判定

セバスは「高度な作業・検証基盤」には到達しているが、「目標を分解し、未達差分を閉じるまで自律的に進み、根拠付きで完了するシステム」には未到達である。

不足の核心は、目標契約、計画被覆、単一状態、次アクション制御、共通完了ゲートの五点である。OCRやモデル性能ではない。この五点を先に統合することで、既存資産を活用した目標達成型へ移行できる。
