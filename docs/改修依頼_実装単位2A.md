# 改修依頼: 実装単位2A(P0-2/P0-3 データモデルと純粋関数)

## 背景
`docs/対応設計_最終版_2026-09-23.md` 第2章(P0-2)・第3章(P0-3)の設計に従う。
単位1(P0-1、`parse_money`・読取失敗issue化)は実装済み・テスト441件合格・pytestはシステムpythonで
そのまま動く(`pip install -e ".[dev,reproduction]"` 済み)。

今回は**単位2A: データモデルと純粋関数のみ**。既存の抽出器(Excel/CSV/PDFアダプター)や
workflow の合格判定ロジックにはまだ接続しない(それは単位2B・2Cで行う)。

## やること

### 1. 新規ファイル `app/vehicle_reconciliation.py`
設計書 第2.2節の仕様どおり:
- `reconcile_sources(records, controls, dispositions, excluded_records, read_issues) -> list[dict]`
  各キー(原本別・会社別・月別・費目別・税区分。請求単位がある費目は invoice_id も含む)について
  `source_total` / `included_total` / `excluded_total` / `unallocated_total` / `unknown_components` /
  `difference` / `status`(`matched|mismatched|unavailable|incomplete`)を計算する純粋関数。
  - `source_total` は `origin='source_total'` かつ `status='available'` の control のみ集計する
    (`origin='sum_of_lines'` は独立合計として使わない)。
  - read_issue が混ざるキーは、差額が0でも `incomplete` にする(matchedにしない)。

### 2. `app/vehicle_auto.py` に型を追加(既存抽出処理は変更しない)
- `InvoiceDocument` dataclass(設計書 第3.1節のフィールドどおり)
- `AdapterResult` dataclass(設計書 第3.4節のフィールドどおり)
- `classify_invoice_relation(a: InvoiceDocument, b: InvoiceDocument) -> Literal[...]`
  設計書 第3.2節の優先規則(exact_duplicate / same_invoice_complement / different_invoice /
  partial_overlap / unknown)どおりに実装する純粋関数。
- これらの型・関数は**新設のみ**。既存の `extract()`・`fuel()` からはまだ呼ばない。

### 3. source_controls のデータ構造
設計書 第2.1節のJSON構造(`origin`, `control_kind`, `status`, `reason_code` 等)を、
コメントまたは型ヒント(TypedDict等)として `app/vehicle_reconciliation.py` に定義する。

## テスト
新規 `tests/test_vehicle_reconciliation.py` を作成し、次を検証する(設計書 第2章「受入条件の検証方法」1〜9、
第3章「受入条件の検証方法」の一部を、純粋関数レベルの単体試験として):
1. 原本統制額1000円、明細600+400円 → matched
2. 400円明細欠落 → 差額400円、mismatched
3. 同一明細重複 → 差額または二重計上検出
4. 根拠付き除外100円 → 取込900+除外100でmatched。理由欠く除外は不合格
5. controlが取得不能 → unavailable、合格にしない
6. `origin='sum_of_lines'` のみのcontrolsでは合格にしない
7. read_issueが混ざるキー → incompleteになる(matchedにならない)
8. `classify_invoice_relation`: exact_duplicate/same_invoice_complement/different_invoice/
   partial_overlap/unknown の各ケースを1つずつ
