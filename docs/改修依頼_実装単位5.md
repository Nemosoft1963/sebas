# 改修依頼: 実装単位5(P1-3 月別配賦・社会保険根拠・判断継承)

## 背景
`docs/対応設計_最終版_2026-09-23.md` 第6章(P1-3)・第11章「実装単位5」に従う。
単位0〜4(P0-1〜P0-3、P1-1第一段階、P1-2)は実装済み・497件合格。

業務確認事項(第13章)は未回答。乗替の「台帳に期間が無いときどうするか」等、未決の間は
確認へ回し、一括配賦・料率推測をしないという安全側の既定を厳守する。

## やること(設計書 第6章 6.1〜6.5節どおり)

### 1. 割当レコード(6.1節)
`AllocationRule`構造(id/subject_type/subject_key/effective_from/effective_to/allocations/
basis_type/basis_evidence/reason/source_hash/created_by/decision_id/status)を実装。
- 期間粒度は**月**。ratio合計1、会社整合、期間重複をvalidatorで検査。合計1超は422。
- 台帳に期間が無ければ対象月全体とし、**複数車両ヒットは自動確定せず確認**(現行の安全側を維持)。
- `payroll` add: その月に有効なassignmentが1件ならその車両100%。複数なら指定ratio(合計1)または確認。
  0件なら現行どおりallocation issue。**グループ全月を一括で1台にしない。**

### 2. decide()(6.2節)
対象を「group全件」から「明示されたissue_idと、同じemployee×monthの明細」へ変更。
全月一括は`apply_to='this_month'|'date_range'`をクライアントが送る(**既定this_month**)。
複数車両は`allocations: [{vehicle_id, ratio}]`をAPIで受け、合計1をサーバー検証。

### 3. 判断継承(6.3節)
再抽出時に旧判断を無条件再適用しない。history のdecisions/assignmentsを読み、
subject key一致・対象月が有効期間内・vehicle IDと会社が現行対象集合に存在・根拠sourceのhash一致
の場合のみ`reused`として再適用。不成立は`unresolved`に戻し、理由`stale_decision`/
`needs_revalidation`/`invalid`。

### 4. 社会保険(6.4節)
- 明示列があるときだけ取り込む(現行維持)。列が無い・読めないときはissue `kind='insurance_basis'`。
  「料率×給与」で埋めない。
- **本人控除列(社会保険料、健康保険料の個人負担等)をinsuranceにマップしない。列エイリアスを拒否リストで固定。**
- `insurance_basis`構造(`kind`/`source_refs`/`rule_version`)を明示額のlocator保存に使う。
  `calculated_from_confirmed_rule`は業務仕様が揃うまで実装しない。

### 5. 仮定ゼロ整理(6.5節)
同一車両×月×費目に`actual`が付いたら、そのキーの`assumed_zero`を削除する正規化関数を作る。
削除履歴はdecision logへ残す。未配賦actualがあるだけでは全車両のzeroを自動削除せず、
配賦確定後に行う。

## テスト
設計書 第6章「受入条件の検証方法」1〜8を実装:
1. 乗替: 同一社員、1-3月車両A、4-7月車両B。給与が月ごとに分かれる。一括Aにならない
2. 複数配賦: 0.5/0.5を保存。calculateが両車両に配分、未配賦0。合計1超・0以下・会社不一致・
   期間重複は422
3. 原本変更: 決定後に給与ブックを差し替え。stale、継承しない。再確認issue。
   ハッシュ不変の再抽出ではreused
4. 未確定条件: 車両0件マッチ。質問が業務事実。読取失敗「要確認」は配賦UIに出さない
5. 社会保険: 会社負担列あり→actual。列なし→insuranceを仮定ゼロにせずissue。
   個人控除列だけあるブック→insuranceに転用しない
6. 車両対象集合から配賦先が消えた場合、旧判断をinvalidにする
7. 実額が入った費目のassumed_zeroが消える。未配賦だけのときは全車両zeroを消さない
8. UIでgroup全月を意図せず単一車両へ一括適用できないこと(API既定this_month)
