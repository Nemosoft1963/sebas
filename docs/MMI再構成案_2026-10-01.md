# セバス MMI再構成案

作成日: 2026-10-01
対象: 統合フロントのプロジェクト作業画面
状態: 2026-10-01にMMI画面を本番反映。実装・検証・未完了事項は `docs/CHANGELOG_2026-10-01_mmi_deployment.md` を参照。ブラウザ視覚確認は未実施。

## 1. 目的

利用者が「いまどのプロジェクトを見ているか」「どこまで進んだか」「何が止めているか」「次に誰が何をするか」を一画面で理解できるようにする。計画や検証の内部データは保持しつつ、通常画面では業務上の意味に翻訳して見せる。特に販売プロジェクトのような長い計画でも、文書作成と実行証拠、人間承認、外部AI接続障害を混同させない。

## 2. 現行画面で確認した問題

| 現行の実装・配置 | 利用者に起こること |
|---|---|
| `projectSelect` は元の「プロジェクトと共有コンテキスト」欄から取り外され、`project_mission.js` が後から作る `.workflow-project` に移される。その直後に5つのタブが並ぶ。 | プロジェクト切替が全タブ共通の親操作であることが見た目から伝わりにくい。元の設定欄には新規・保存・削除などが残り、選択欄との関係も離れる。 |
| `workflow_readiness.js` は「進行状態」をタブより上に挿入する。目標検証は「計画内容」内、実行状態は「実行モニタリング」内に分かれる。 | 状態、停止理由、外部検証結果、次操作を探し回る必要がある。 |
| `project_mission.js` の計画一覧と工程詳細は `acceptance_criteria` をそのまま表示する。 | JSON形式の成果物契約が「完了判定」として表示され、必要な確認事項が読めない。 |
| `goal_review.js` は検証結果全体、修正履歴、変更前後を `<pre>` のJSONとして表示する。 | 合否、指摘、接続エラー、修正内容の区別が難しい。 |
| 工程結果や一部の詳細画面も生のJSONや長文を表示する。 | 初めて使う人には現在の状態と次の行動が埋もれる。 |
| タブ選択は `localWorkflowTab` という全プロジェクト共通の記録。 | プロジェクト切替後も前のプロジェクトで開いていたタブが残り、文脈が分かりにくい。 |

根拠となる主なファイル: `app/static/index.html`、`app/static/project_mission.js`、`app/static/workflow_readiness.js`、`app/static/goal_review.js`、`app/static/project_mission.css`。

## 3. 提案する情報構造

プロジェクト選択を画面最上部の固定した「作業対象」帯へ置く。その下に、**選択中のプロジェクト内のメニュー**としてタブを配置する。全体設定やAI会話はプロジェクト内の主要工程と混在させない。

```text
┌ セバス ────────────────────────────────────────────────┐
│ 作業対象: [本システムを販売実行 ▼]  [新規作成]  [設定] │
│ 目標: 法人向けAI導入支援の販売   計画 v33   状態: 計画修正中 │
├ 概要 │ 目標と計画 │ 実行と確認 │ 成果物 │ 履歴 ────────┤
│ いまの状態: 外部検証で指摘あり                         │
│ 止まっている理由: 計画の内容指摘 / OAuth再認証が必要    │
│ 次の行動: 計画の指摘を確認して修正する                   │
│ 担当: システム / 人間     [指摘を見る]                  │
│ 達成条件: 合格 x / 未達 y / 未確認 z   工程: 完了 a/20 │
└────────────────────────────────────────────────────────┘
```

- **概要**: 状態、停止理由、次の一手、担当、進捗、未達条件を表示する。各カードから該当画面へ移動できる。
- **目標と計画**: 目標・達成条件、計画一覧、工程依存図、外部AI検証、指摘反映、計画承認を順に配置する。依存図は補助表示にする。
- **実行と確認**: 実行操作、工程別の進捗、承認待ち、業務確認事項、実行証拠、障害時の再開案内をまとめる。
- **成果物**: 生成済み成果物を「下書き・暫定・検証済み・人間承認済み」で区別し、プレビューとダウンロードを置く。RAG登録は人間承認済みの結果からのみ進める。
- **履歴**: 判断履歴、外部AIの指摘履歴、操作記録、変更履歴を時系列で表示する。プロジェクト名・固定コンテキスト・外部AI設定は右上の「設定」で扱う。

タブを切り替えても作業対象帯と状態要約を常に表示する。プロジェクトを切り替えたら見出し・進捗・操作ボタン・入力内容を一括で切り替え、前プロジェクトの一時入力を混ぜない。タブ記憶はプロジェクト単位にする。プロジェクト未選択時は新規作成と選択を案内する。

## 4. 状況表示の文章化

画面上部の状態カードは常に次の5項目を同じ順で表示する。

1. **現在**: 例「計画を作成済み。外部AIの確認で修正が必要」
2. **止まっている理由**: 例「計画内容の指摘が3件」「Googleの再認証が必要」などを別行に表示
3. **次の操作**: 動詞で始める一つの推奨操作と、その画面を開くボタン
4. **担当**: 「セバスが自動処理」「人間が確認・承認」「外部サービスの復旧待ち」
5. **達成の証拠**: 成果物、公開URL、投稿URL、回答同期、人間確認などの必要数と確認済み数

状態コードは表示専用の辞書で日本語へ変換する。`not_passed` は「計画内容の指摘あり」、`connection_failed` は「外部AIに接続できない」、`waiting_budget` は「利用枠の回復待ち」、`unverified` は「未検証」とする。原因が複数ある場合は「計画内容」と「接続・認証」を別カードにする。`0件` と「未取得」「不明」を同じ表現にしない。未承認・未検証・失敗も成功と表示しない。

ボタンが使えない場合は、ボタンの近くに理由と解除方法を表示する。`title` 属性だけに理由を隠さない。HTTPエラーの生本文は通常画面に出さず、「Google接続の再認証が必要」「一時的な503。後で再試行」などに変換する。詳細コードは「技術情報を表示」の中に残す。

## 5. JSONを人間が読める表示へ変換する

APIと保存データのJSON契約は変更せず、表示層に `statusPresenter` / `planContractPresenter` / `reviewPresenter` 相当の変換関数を設ける。未知の値は「不明」と表示し、推測して埋めない。原文JSONは折りたたみの「技術情報」から確認・コピーできるようにする。

| 生データ・現行箇所 | 通常表示の例 |
|---|---|
| `acceptance_criteria` / `workflowPlanTasks`、`workflowTaskDetail` | 「この工程で作るもの」「必要な入力」「先に終える工程」「人間確認」「完了の証拠」「未達ならどうなるか」の見出し付きカード。JSON文字列の全文は通常表示しない。 |
| `plan_review` / `goalPlanResult` | 「全体判定」「合格 0/5」「内容の指摘」「接続できなかったAI」の各カード。AIごとに判定、重要度、指摘、修正案を表にする。 |
| `revision_history` / `goalFeedbackHistory` | 日時・計画版・対象工程・変更概要・反映済み/未反映を一覧化。差分は変更点だけを先に見せる。 |
| `diff.before` / `diff.after` | 「人間確認: 不要 → 必須」「依存工程: SC06を追加」などの項目差分。全文は詳細表示。 |
| 工程の `result` / `error` | 「処理結果」「作成物」「失敗理由」「再実行できる範囲」「次の操作」。長いログ・内部形式は詳細表示。 |
| `workflow-readiness` の `phase`、`next_action`、`gate` | 日本語の段階名と、未達の達成条件ごとの不足証拠。APIパスは利用者向け本文に出さない。 |

文言例: 「計画検証は未合格です。Claudeは計画内容を条件付きと判定、ChatGPTは情報不足、Grokは不合格。Geminiは一時的な接続障害、Metaは認証設定が必要です。」この例は2026-10-01の販売計画v33の観測値であり、画面は常に最新APIから生成する。

## 6. 実装範囲と順序

| 優先 | 改修 | 主な場所 | 完了条件 |
|---|---|---|---|
| P0 | プロジェクト帯をタブの親として固定し、設定操作を整理する | `index.html`, `project_mission.js`, `project_mission.css` | 切替中の対象が全タブで明確。狭い画面でも選択欄とタブが重ならない。 |
| P0 | 概要カードを `workflow-readiness` から構成し、停止理由・次操作・担当を一箇所に集約する | `workflow_readiness.js`, `project_mission.js` | 外部検証失敗、接続障害、人間確認待ちが別表示になる。 |
| P0 | 計画契約と外部AI検証のJSONをカード・表へ変換する | `project_mission.js`, `goal_review.js`, 共通表示モジュール | 通常操作で生JSONが見えない。必要な技術情報は詳細から確認できる。 |
| P1 | 計画・実行・成果物・履歴の画面再配置、プロジェクト単位のタブ記憶 | 各 `app/static` 画面 | プロジェクト変更時に古い入力・結果が混ざらない。 |
| P1 | 状態ごとの次操作リンクと無効ボタン理由、空状態、モバイル表示、キーボード操作を整える | 共通UI、各画面 | 利用者が停止理由と次操作を画面上で説明できる。 |

既存API、承認ゲート、OCRの未承認遮断、RAG登録条件は維持する。UIの整頓によって未達を達成済みへ書き換えない。内部JSONは監査用に保持し、通常画面への直接表示だけをやめる。

## 7. 受入シナリオ

1. 販売プロジェクトを選ぶと、上部にプロジェクト名・計画版・未合格理由・次の操作が表示される。タブを移動しても作業対象が消えない。
2. 別プロジェクトへ切り替えると、計画、検証結果、進捗、入力欄がそのプロジェクトの内容に変わる。前のプロジェクトの結果や承認チェックは残らない。
3. 計画工程を開くと、必要な入力・成果物・承認・証拠が日本語の項目として読める。通常画面にJSON文字列は出ない。
4. 外部AIの「計画内容の指摘」と「HTTP 401/503などの接続障害」が別の原因として表示される。未検証を合格と表示しない。
5. Google OAuth再認証が必要な場合は、人間の操作内容と再開条件を案内する。再認証前の同期は完了と表示しない。
6. キーボードだけでプロジェクト選択、タブ、次操作へ移動でき、画面読み上げでは現在タブと状態更新が分かる。
7. 主要な画面幅（デスクトップ、タブレット、スマートフォン）で表示を確認し、実案件のスクリーンショットと操作記録を保存する。

## 8. 設計上の判断

最初の表示は「概要」にする。利用者が先に知りたいのは計画の内部構造ではなく現在地と次の行動だからである。計画承認、外部送信、公開、RAG登録などの操作は従来どおり個別の人間確認を要する。状態を分かりやすくしても、承認条件は緩めない。
